## 问题与现场证据

批量删除首条 2112782755998449991 提示“实时账号或帖文核验不通过，未发送删除”，其余 15 条停止。原逻辑强制从分析接口再次读取目标帖及正文，任意单条失败后停止整批。

CDP 只读检查显示：账号绑定正确，分析接口 HTTP 200，但当天的 188 条记录里没有目标 ID；TweetDetail 同样 HTTP 200，但目标 entry 的 tweet_results 为空。旧流程因此在发送删除前停止。分析列表缺帖不能证明登录失效，也不应成为删除前置条件。

最初尝试增加三小时账号缓存和缺帖兜底。用户随后明确纠正：这是删除与分析的关系粘连，应直接请求删除，由 X 处理存在性、所有权和权限；单条失败不能终止批量任务。本篇按同一需求的澄清更新，旧缓存方案已撤销，delete-preflight.js 已移除，不再读写核验缓存。

## 最终行为

1. 用户确认具体帖子 ID 后，直接提交 DeleteTweet。删除执行页只要求 X 页面加载完成，不再要求 contentPageQuery 模板，不打开分析页、不读取分析数据、不做正文比对，也不预先读取帖子详情。
2. 存在性、登录账号是否拥有帖子、删除权限等由 X 删除接口判断，不额外构造前置网络请求。
3. 单次确认、有效期、本地账号绑定、帖子保护及写入前持久化防重继续保留。正文快照只供确认展示，不再影响按 ID 删除。
4. X 明确返回删除成功回执时记录成功。HTTP 200 但缺少成功回执不能当作成功；错误响应记录失败原因；超时等不明确结果记录为待确认，不自动重发。
5. 不再自动读取详情等待删除后可见性变化。结果待确认的帖子仍可通过原有独立核验入口检查，不阻塞后续删除。
6. 批量逐条捕获异常、保存结果、继续下一项。403、404、429、GraphQL 错误、网络异常、单条本地条件变化以及结果待确认均不会触发整批停止。共用执行页无法准备时，所有尚未执行的条目分别记录未发送及原因。
7. 正常完成全部条目后，返回 completed 或 completed-with-errors；界面统一展示已删除、未成功、未执行及逐条原因，确认弹窗不再声称失败即停止。

## 实时进度完善

同一删除需求的交互完善，在原文补充，不另立编号。

- 开始准备时显示“准备删除 0/16”，实际进入每条删除前显示“正在删除 1/16”“正在删除 2/16”，直到最后一条。
- 后台在每条执行前持久化 currentIndex，每条执行后保存结果；进度接口同时返回总数、已处理数、当前序号和批次状态。当前序号表示正在处理的第几条，不表示已经成功删除几条。
- batchDeleteProgress 是独立只读操作，不占用删除任务锁，因此删除进行中也可读取进度；该读取只访问本地批次，不请求 X。
- 面板首次在 200 毫秒后读取，之后每次读取结束再等待 500 毫秒。请求不重叠；完成或组件卸载时停止轮询，并通过代次校验丢弃晚返回的响应。
- 个别删除失败仍推进到下一条；进度读取失败则保留最后已知进度，既不停止删除，也不额外弹出提醒。最终结果由删除任务统一报告。

## 本次明确的产品设计原则

以下是用户在本轮明确的产品要求，落实到删除流程的验收标准，不是增加技术检查的依据。

1. 围绕用户完成目标设计流程。删除本身不依赖分析；接口已能判断存在性、归属和权限，就不为这些事项重复增加前置门槛。
2. 可恢复的准备工作和异常由程序处理，保留用户选择与任务进度；辅助检测失败不能直接等同于业务操作失败。
3. 将失败影响限制到具体条目。批量操作应处理全部已确认条目，并统一呈现结果，不能把单条错误升级为整批中止。
4. 进度在用户正在操作的位置简洁显示，不为正常处理、重试或内部状态变化增加弹窗和确认。
5. 主动要求用户介入，应当确实属于“任务无法继续完成”或“必须由用户确认、提供信息、手动协助”。说明影响和所需的最小行动，不让用户自行解释内部报错。
6. 低打扰不等于隐瞒结果。成功、失败和待确认都应可查；对于不明确的写入结果，不假报成功、不自动重复发送。
