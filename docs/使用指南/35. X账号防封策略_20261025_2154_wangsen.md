# 没到 400 次，为什么 X 还是限制你？关注与取关避坑指南

> 依据核对日期：2026-10-25。面向使用关注管理、回关监控和取关队列的账号运营者。目标是减少误操作、限流与账号受限风险，不承诺任何参数可以保证不封号。

你可能遇到过这样的情况：主页可以正常浏览，工具也在运行，却突然无法关注；或者明明每天只处理几十个人，仍然收到限制提示。

问题往往出在把三个不同概念混在一起：平台公布的技术上限、工具设置的执行额度，以及账号行为是否符合规则。调整一个数字，不能同时解决这三个问题。

## 一、400 和 5,000，究竟限制什么？

| 数字或行为 | X 官方说明的含义 | 使用时应如何理解 |
| --- | --- | --- |
| 每日最多关注 400 个账号 | 新增关注的技术上限 | 不能把它当作取关额度，也不应以每天用满为目标 |
| 已关注达到 5,000 个账号 | 后续新增关注受到账号自身关注与粉丝比例影响 | 官方没有在该页面公布统一比例公式，不能自行套用“80%”等阈值 |
| 反复关注后取关以增加粉丝 | 官方列为 follow churn，即关注关系操纵 | 把动作拆散到不同时间，不会改变行为目的 |
| 短期大量关注或取关无关账号 | 属于官方列出的滥用行为，自动化尤其需要注意 | 低于日上限仍可能受限 |

这些规则来自 [X 官方关注限制说明](https://help.x.com/en/using-x/x-follow-limit)。该页仍标有 March 2019，本文记录的是核对日可访问的公开内容，不代表 X 公开了完整风控模型。

## 二、自动取关没有一个公开的“保号秒数”

X 的账号行为说明直接表示不允许自动主动关注和自动取关。自动化规则另强调禁止批量、激进或无差别关注与取关，并禁止通过网页脚本等非 API 自动化方式操作网站。不能用其中措辞较宽的一段，推导出另一段已经失效。[账号行为说明](https://help.x.com/en/rules-and-policies/x-rules-and-best-practices)、[自动化规则](https://help.x.com/en/rules-and-policies/x-automation)。

因此，以降低账号风险为首要目标时，更合适的工作流是：工具整理关系、识别待核实账号、展示候选与历史，用户根据实际需要决定是否操作。对不符合规则的自动化行为，调慢速度不能消除规则风险；调用网站内部接口也不能据此宣称获得了官方授权。

随机间隔可以减少请求集中发生，但无法证明平台会将这些操作视为正常人工行为。不要把“模拟真人”“每天低于某个数”写成保号承诺。

## 三、开源取关工具实际用了多快的速度？

我们克隆并检查了 `kysoog/x-unfollowers` 的提交 `35f8a6fe6b05686b0519f97ad220337f9ab09e25`。实际实现如下：

| 设置 | 源码实际行为 |
| --- | --- |
| 默认每人间隔 | 随机 3–8 秒；等待当前请求结束后才进入下一人 |
| 默认每日额度 | 200 次成功取关；设为 0 表示不限 |
| README 建议 | 间隔 5–15 秒、每次 50–100 人，属于作者建议 |
| 单批硬限制 | 没有每批 100 人的代码限制，主要由所选队列和每日额度约束 |
| 遇到 429 | 等待 60–120 秒乘以重试序号，最多重试 4 次；耗尽后跳过当前账号继续队列 |
| 遇到 401/403 | 暂停队列，要求重新核对登录状态 |
| 重启恢复 | 从本地保存的队列恢复；0.4 分钟闹钟用于唤醒恢复，不是取关间隔 |

可核对 [默认设置源码](https://github.com/kysoog/x-unfollowers/blob/35f8a6fe6b05686b0519f97ad220337f9ab09e25/utils/storage.js#L32)、[队列与重试源码](https://github.com/kysoog/x-unfollowers/blob/35f8a6fe6b05686b0519f97ad220337f9ab09e25/background.js#L327)和 [README](https://github.com/kysoog/x-unfollowers/blob/35f8a6fe6b05686b0519f97ad220337f9ab09e25/README.md#L133)。

这些数字证明工具如何实现，不证明其参数安全。特别是“限流后继续换下一个账号”和“请求结果不明时自动重试”，都不适合直接复制到强调防重复操作的系统中。

## 四、每日 100 人，应当是一道额度门槛

XFollower 当前 2.15.7 将每日默认取关额度设为 **100 人**，同时保留每轮最多 1 人、两次请求至少间隔 30 分钟的限制。默认调度周期为 45±15 分钟，默认窗口为 09:00–21:00。

额度与吞吐需要一起看：

- 默认 12 小时窗口，按最短 30 分钟间隔计算，理论上最多约 24 次；按平均 45 分钟计算约 16 次。
- 当前实机自定窗口为 01:00–23:00，共 22 小时；相同最短间隔下理论上最多约 44 次。
- 上述计算忽略了请求耗时、浏览器休眠、无候选、核验失败等因素，实际完成量可能更低。

所以，设置 100 人不会让队列自动加速到每天完成 100 人。原先的 12 人硬上限已撤销；100 人额度和至少 30 分钟间隔均属于产品配置，**不是 X 官方给出的安全值，也不是开源项目验证过的结论**。判断配置是否合适，应同时看真实需求、规则边界和执行记录，而非只看额度数字。

## 五、把风险控制放进队列的每一步

以下是工程上的可靠性建议，用于避免误取关和重复提交；它们不能替代平台规则。

**入队前：明确目标与依据。** 整理真正不再需要关注的账号，记录来源、发现时间和最新关系。不要仅因为短期没有回关，就反复执行关注—取关—再关注的循环。把关系不明的账号放入待核实列表。

**出队前：重新核验。** 确认当前登录账号与任务绑定账号一致，检查目标身份、关注关系、白名单和豁免状态。候选进入队列后，用户可能已经回关或被手动保留，旧快照不能直接作为执行依据。

**执行中：逐个发送。** 同一账号只允许一个取关任务提交请求。先持久化目标和请求状态，再调用接口；不要在多个面板、多个批次中同时处理同一目标。

**响应后：核对真实结果。** 请求超时不等于失败，也可能已经生效。结果不明时暂停该目标的重试并复查实际关系；确认完成后再出队、回写本地记录。重启后恢复队列时，也应先处理未确认请求。

**统计时：同时记录尝试与成功。** 失败请求仍可能消耗接口额度。只按成功人数计数，会掩盖大量无效请求。日志至少保留目标、阶段、是否发出请求、HTTP 状态、复查结果和下一步处理方式。

## 六、看到限制提示，先定位再恢复

“You are unable to follow more people at this time”可能涉及每日新增关注额度、短时过快、关注比例限制，或账号锁定。官方给出的恢复条件因原因而异，不能统一理解为“等一小时必定恢复”。[X 官方说明](https://help.x.com/en/using-x/x-follow-limit)。

| 观察到的现象 | 应做的检查与处理 |
| --- | --- |
| 用户资料接口 429 | 暂停相关资料请求；确认本轮是否根本没有发送关注或取关请求 |
| 关注或取关接口 429 | 停止受影响的写操作批次，记录返回的限流信息；不要立即遍历队列继续撞同一限制 |
| 请求超时或连接中断 | 标记结果待确认，复查关系后再决定下一步 |
| 401/403 | 核对响应正文、登录状态和账号提示；不能把所有 403 都当作登录过期 |
| 浏览正常，但操作被拒绝 | 按具体接口检查；能浏览页面不代表写操作有额度 |
| 账号出现锁定或验证提示 | 停止自动操作，按 X 页面要求处理，不通过换账号或轮换身份绕过限制 |

恢复前，应确认异常原因已经解除、未确认请求已经核实、下一轮仍按正常队列顺序执行。错过的任务不要在恢复瞬间集中补跑。

## 七、怎样判断队列真的健康？

不要只看界面上的“正在运行”。至少应当能从日志回答：

1. 本轮何时触发，是否处于用户设定的执行时段？
2. 实际检查了多少候选，哪些因关系变化而跳过？
3. 是否发送了请求，向哪个目标发送，结果是否确认？
4. 成功记录是否出队，重启后是否会重复处理？
5. 遇到错误后是否停止了相应操作，下一次计划是否存在？

CDP 只读监控可以辅助检查这些问题；模拟测试可以验证代码路径。两者都应与真实操作验收区分开，不能把“单测通过”写成“已经成功取关”。本文核对时，真实账号的自动取关闭环仍在观察中。

把工具用于整理关系、发现问题和记录证据，把每一次外部操作控制在明确授权与可核实的范围内，才能让账号运营更可控。任何声称“设成某个秒数就永不封号”的方案，都缺少足够依据。
