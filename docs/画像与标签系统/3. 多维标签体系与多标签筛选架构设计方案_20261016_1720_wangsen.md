## 一、方案背景与核心痛点

在当前的 XFollower 系统中，候选账号的画像与标签体系相对单薄：
1. **标签维度单一**：仅有二元的“互粉 / 无”以及“推荐 / 不推荐”，无法区分账号的垂直赛道、粉丝量级、活跃周期与互动风格；
2. **打标来源缺乏分层**：单纯依赖前端粗粒度关键词匹配与单次 Grok 简单回填，无法支持“本地轻量正则 + Grok 深度语义 + 人工自选修正”的三级融合；
3. **缺少标签组合筛选能力**：现有的列表仅支持单一关键字搜索（`#mutualSearch`），用户面对上千个候选账号时，无法按“蓝V + AI赛道 + 高回关率”等复合特征快速筛选目标；
4. **自动化与回评缺乏个性化依据**：自动化看帖关注和 Grok 回评时，如果能获取多维标签（如语言偏好、擅长赛道、互动风格），回评内容将更加精准，回关率能显著提升。

本方案旨在设计一套**结构化、可扩展、多层级**的多维标签引擎，并提供直观易用的**标签胶囊过滤与复合筛选器**。

## 三、三层融合打标流水线（Labeling Pipeline）

为了在**执行效率（毫秒级）**与**语义深度（精准画像）**之间取得平衡，设计“三层渐进式”打标架构：

```mermaid
flowchart TD
    Raw[新账号 Profile & 最近推文] --> L1[第一层: 本地规则引擎 (L1 Rule Engine)]
    L1 --> Cache1[实时生成基础标签: 蓝V / 赛道词 / 诚信互关]
    
    Cache1 --> Choice{是否需要深度解析?}
    Choice -- 否/已满足门槛 --> Store[(持久化到 IndexedDB)]
    Choice -- 是: 点击Grok分析/自动化入池 --> L2[第二层: Grok 语义分析引擎 (L2 Grok Engine)]
    
    L2 --> GrokJSON[Grok 返回结构化 JSON 标签]
    GrokJSON --> Merge[置信度加权合并]
    Merge --> Store
    
    Store --> L3[第三层: 人工标注与覆盖 (L3 Manual Override)]
    L3 --> Final[最终生效标签集合]
```

### 3.0 零额外开销的数据沉淀机制（“顺水推舟”式中台）

> [!IMPORTANT] 核心原则：绝不为了打标签而专门发起多余的模拟跳转或独立爬取
> 为标签专门写爬虫或模拟点击主页，极易触发 X 平台的频率限制与风控封禁，还会导致机器卡顿。我们必须**“顺水推舟”**，全面复用系统已有的 4 大高频业务流程中天然拦截或加载到的原生数据：

```mermaid
flowchart LR
    subgraph NaturalFlows [已有高频业务流程]
        F1["① 互粉追踪 / 增量拉取<br>(Following/Followers接口)"]
        F2["② 提取推文评论及用户<br>(TweetDetail评论树)"]
        F3["③ 自动化看帖关注<br>(最新推文与互动量)"]
        F4["④ 回关监测周期轮询<br>(关系变化与回关耗时)"]
    end

    NaturalFlows --> Ingest["数据中台: 顺手沉淀至 IndexedDB<br>(Profile / 评论文本 / 互动时间戳)"]
    Ingest --> L1["L1 本地规则引擎 (即时秒级计算 80% 基础标签)"]
    L1 --> Queue["低置信度 / 疑难账号加入待分析队列 (Batch Queue)"]
    Queue --> GrokTimer["后台空闲时定时微批量 (5~10账号/次) 调取 Grok"]
    GrokTimer --> FinalDB["多维画像沉淀入库 (零额外页面操作)"]
```

1. **场景 ①：互粉追踪 / 粉丝增量拉取时**：
   - `network-api.js` 在拦截或调取 X 官方 `Following` / `Followers` GraphQL 响应时，返回体本身已完整包含每个用户的 `rest_id`、`name`、`description (Bio)`、`followers_count`、`friends_count`、`is_blue_verified` 等丰富画像；
   - 系统在更新粉丝列表的同时，**顺手写入画像缓存表**并即时跑一遍本地规则计算，整个过程耗时仅几毫秒，不增加任何网络请求。
2. **场景 ②：提取推文评论与评论用户时**：
   - `tweet-comment-button.js` 拦截推文详情（`TweetDetail`）时，每个发评者的 Profile、其**发表的具体评论正文**、以及**原推文主题**均已完整暴露；
   - 评论内容和原推文内容是判断用户“互动风格、赛道领域、真实语言偏好”的最强特征，提取评论时**顺手存下该互动样本**，直接为用户画像注入第一手动态素材。
3. **场景 ③：自动化看帖关注时**：
   - 自动化进入博主最新推文看帖时，页面已经加载了该博主最近一条推文的发布时间戳（`created_at`）、推文互动率与发帖类型（原创 vs 纯转发）；
   - 关注动作触发前，**顺手提取并更新**该用户的“活跃度时间戳”，日更高频/沉睡状态随之被自然刷新。
4. **场景 ④：回关监测周期轮询时**：
   - 后台定期扫描已关注列表中是否有新回关用户，比对 `followedAt` 与回关探测时间，**顺手沉淀**其“回关时效（秒回 / 慢热 / 超期不回）”的信誉特征。

### 3.1 第一层：本地规则引擎（L1 毫秒级运算）
- **触发时机**：在上述 4 大场景顺手获取数据时，在客户端本地线程中同步完成；
- **计算逻辑**：
  - 基于关注数/粉丝数比例算术计算（`1/5 推荐` 规则，判定诚信或骗关）；
  - 预编译的正则表达式词库（中英文双语 Niche 词汇典 + 互粉热词表）；
  - 最近推文的时间戳计算活跃度（近 24 小时、近 7 天、沉睡期）。
- **特点**：零 API 成本、100% 离线可用、支撑千级数据瞬间打标。

### 3.2 第二层：Grok 深度语义微批量分析（L2 智能识别）
- **触发机制**：
  - **空闲时微批量触发（Micro-Batch）**：对于本地词典未命中（置信度低）或新入库的高价值账号，不单次频繁调用，而是放入 `pending_grok_queue`，在后台空闲时**按 5~10 个账号合并为一个 Batch 请求**提交给 Grok，大幅节省 Token 与请求频次；
  - **零模拟页面操作**：直接使用顺手沉淀在数据库里的 `Bio`、`最近推文/评论正文` 发起 API 请求，**完全不需要模拟浏览器打开主页或滚动页面**，规避任何风控风险。
- **提示词升级（Batch Prompt）**：
  要求 Grok 对批量输入的账号信息输出结构化 JSON 数组：
  ```json
  [
    {
      "handle": "tech_runner",
      "reputation": "quick_back",
      "niche": "ai_tech",
      "role": "creator",
      "confidence": 0.95,
      "summary": "AI独立开发者，评论互动积极，求互粉意愿强烈"
    }
  ]
  ```
- **融合策略**：Grok 标签对同维度规则标签进行**覆盖或提升置信度**，若规则判为 `泛生活` 但 Grok 识别出为隐晦的 `Web3 开发者`，以 Grok 深度语义为准。

### 3.3 第三层：人工管理与白名单覆盖（L3 绝对优先级）
- **交互位置**：账号列表行内标签区、右侧「资料抽屉」头部；
- **能力**：
  - 用户可点击标签旁的 `+` 快速追加任意系统标签或自定义文本标签；
  - 用户可点击已有标签的 `×` 移除误标的标签；
  - 支持一键标记「🛡️ 白名单（免取关）」和「⭐ 重点跟进」；
  - **优先级**：人工标记具有最高优先级（`source: 'manual'`），后续规则重算或 Grok 批量更新均不得覆盖人工标记。

### 4.2 筛选引擎设计与运算逻辑
- **维度内与维度间运算**：
  - **默认模式（智能兼顾）**：
    - 同一维度内多选为 `OR`（如赛道勾选了 `AI` 和 `Web3`，命中任一赛道即可）；
    - 不同维度间为 `AND`（如选了 `🤝诚信互关` 且 选了 `🔷蓝V认证`，必须两个特征同时具备）；
  - **高级开关**：
    - 提供「一键排除骗关/高风险号」复选框，即 `AND NOT high_risk AND NOT marketer`；
    - 提供 `AND / OR` 切换单选按钮，满足灵活度需求。
- **高性能内存倒排索引（Inverted Index）**：
  - 针对面板内存中的 `rows` 列表（通常千级），在加载和过滤时维护标签索引字典：
    ```javascript
    const tagIndex = {
      'reputation:quick_back': Set(['alice', 'bob', ...]),
      'niche:ai_tech': Set(['alice', 'david', ...]),
      'identity:blue_v': Set(['charlie', ...])
    };
    ```
  - 用户勾选或取消标签时，直接通过 `Set` 的交集（Intersection）与并集（Union）运算，在 **< 5ms** 内完成过滤并刷新分页表格，毫无卡顿感。

## 五、底层数据结构升级与向下兼容方案

### 5.1 数据模型扩展定义

在当前账号对象（`User Object`）中，扩展标准化的标签容器：

```typescript
interface AccountUser {
  handle: string;
  name: string;
  bio?: string;
  followersCount: number;
  followingCount: number;
  
  // === 原有字段（保持完全向后兼容） ===
  mutualTag?: string;           // 兼容旧版: '互粉' | '无'
  recommendLabel?: string;      // 兼容旧版: '推荐' | '不推荐'
  recommendReason?: string;
  
  // === 新增多维标签体系 ===
  tags: string[];               // 标准标签数组: ['reputation:mutual_credit', 'niche:ai_tech', 'identity:blue_v']
  customTags?: string[];        // 用户自由文本标签: ['老乡', '出海交流群', '待合作']
  tagDetails?: {
    [tagKey: string]: {
      source: 'rule' | 'grok' | 'manual'; // 打标来源
      confidence?: number;                // 置信度 (0~1)
      assignedAt: string;                 // 打标时间 ISO
      reason?: string;                    // 打标依据
    }
  };
}
```

### 5.2 向下兼容与平滑迁移策略
1. **老数据无感知升级**：
   - 当读取既有存储中的数据时，如果账号对象没有 `tags` 数组，系统自动调用迁移适配器 `normalizeAccountTags(user)`，将旧版的 `mutualTag` 与 `recommendLabel` 转换为 `['reputation:mutual_credit']` 等初始标准标签；
2. **渐进式打标填充**：
   - 首次升级后，系统利用本地闲置时间对已有缓存数据运行 L1 本地规则引擎，逐步回填全量账号的基础标签，不需要消耗网络请求和 Grok 额度；
3. **IndexedDB 存储安全**：
   - 数据依然通过 `persistent-db.js` 的 `durableSet` 统一存取，数据格式为平铺 JSON，无 Schema 破坏性变更风险。

## 六、与现有核心业务的深度联动

多维标签不仅是静态展示，更是整个工具流的**智能化引擎**：

1. **与互关追踪自动关注联动**：
   - 在互关追踪的自动关注设置抽屉中，原有的二元选择“仅关注有互粉标签用户”，升级为**“目标人群精准定位”**：
     - 支持指定：仅自动看帖并关注包含 `[⚡秒回关]` 或 `[💻AI/科技]` 或 `[🔷蓝V]` 的高潜力用户；
     - 自动排除包含 `[⚠️骗关风险]` 或 `[📢营销号]` 的账号。
2. **与 Grok 自动回评深度联动**：
   - 在 `grok-comment.js` 装配 Prompt 时，将识别出的领域和身份标签注入给 Grok：
     > *“目标博主标签为 [💻AI/科技]、[🔷蓝V创作者]，请以同行独立开发者的真诚视角，针对其推文撰写共鸣深刻的互动评论。”*
   - 大幅避免千篇一律的机械套话，显著提高推文回复的质量与博主回关转化率。
3. **与回关监测超期取关联动**：
   - 拥有 `[🛡️白名单]` 或 `[⭐重点标星]` 标签的用户，受到最高等级保护，回关监测无论超过多少天，绝对不会自动触发取关。

### 6.1 内容风险标签与账号证据汇总

新增风险标签时，区分帖子级事实和账号级汇总，避免仅凭一条帖子给作者贴固定身份标签。建议帖子标签键包括 `risk:political_content`、`risk:military_content`、`risk:sexual_content`、`risk:suggestive_content`、`risk:sensational_content`、`risk:violent_extremist_content`。每条标签记录 `postId`、来源 URL、分类器/规则版本、置信度、证据片段、时间和人工复核状态。

账号 `tags` 可展示风险摘要，但必须能展开查看支撑它的帖子证据、数量、时间范围及撤销入口。普通政治或军事题材只表示内容主题；不得直接标成“政治人物”“军事人员”或“极端分子”。“疑似暴力极端内容”只用于有明确暴力鼓吹、招募或行动动员证据的帖子；争议语境进入待复核状态。

风险主题标签与关注/评论的跳过策略分开配置：帖子命中则跳过该帖的 Grok 生成与发布；账号汇总达到用户配置的主题、次数和时间范围后才跳过整个账号。用户要求的政治、军事、色情/擦边类别默认纳入过滤，猎奇作为可选过滤类别。筛查失败或低置信度时暂停自动互动并解释原因，不能按无风险继续。提示词拦截之外，执行流程仍需在关注前、生成前和发布前做本地策略校验。具体队列状态、提示词约束与验收用例见 [Grok 内容风险拦截方案](./互粉与粉丝管理/4.%20Grok引用评价与发布验收_20261016_1818_wangsen.md#content-risk-gate)。

#### 6.2 2026-10-20 危险标签体系与排除高危筛选落地 (v1.7.0)

已在代码中完整落地 7 大内容风险维度标签及筛选引擎闭环：
1. **标准化危险标签字典（`scoring.js` & `content-risk.js`）**：
   - `risk:politics`：`🏛️ 涉政`，标红警示，涵盖政权更迭、高层政争、维稳抗议、政治运动等；
   - `risk:military`：`⚔️ 涉军`，深紫警示，涵盖战役空袭、导弹轰炸、军演对抗、武装冲突等；
   - `risk:religion`：`🕊️ 涉宗教`，深蓝警示，涵盖邪教组织、宗教极端狂热、圣战冲突等；
   - `risk:violence`：`🚫 暴力`，高危深红，涵盖恐怖袭击、恶性虐杀、人体伤害、自残自尽等；
   - `risk:pornography`：`🔞 色情`，高危暗紫，涵盖成人AV、露点性交、生殖器、OnlyFans买卖等；
   - `risk:suggestive`：`👙 擦边`，橙红警示，涵盖福利姬、同城约炮、情色私房写真、低俗引流等；
   - `risk:sensational`：`👁️ 猎奇`，深橙警示，涵盖人体畸形、变态受虐、排泄物恶心等猎奇重口。
2. **规则引擎与画像打标集成**：
   - `computeMultiDimensionTags` 自动对用户简介与前 10 条推文进行 L1 规则检测，命中后生成对应标签与风险证据；
   - `riskAssess` 深度集成内容风险分类器，命中任一高危标签自动判定 `level: 'danger'`。
3. **UI 标签样式与「排除高危」筛选器（`panel.html` & `brand-layout.css`）**：
   - 严格遵循 12px 字体与 24px 高度规范，配备警示配色徽标；
   - 互关追踪标签筛选工具条新增 `[🚫 排除高危]`（`exclude:risk`）胶囊按钮，勾选后毫秒级一键排除任何带有涉政、涉军、涉宗教、暴力、色情、擦边、猎奇标签的账号。
4. **二级复合安全打标与防重缓存机制**：
   - **Level 1（本地关键词粗匹配）**：快速短路，节省 Grok 额度；一旦命中涉政、涉军、涉宗教、暴力、色情等敏感词，立刻终止后续关注与引用评价，直接跳过账号；
   - **Level 2（Grok 深度语义打标）**：若 Level 1 未命中，提取账号主页（Bio）+ 前 10 条推文提交给 Grok 深度语义研判；
   - **持久化防重标识（`grokAssessedAt` / `grokRiskAssessment`）**：打标结果持久化写入账号档案，再次扫描时直接复用缓存，绝不重复调用 Grok 浪费额度；
   - **Grok 风险熔断**：若 Grok 返回标签中包含任一危险标签，立即中止后续操作（不关注、不发评），调度安全置为 `skipped`。
5. **测试验证**：
   - 自动化单测覆盖 7 大维度敏感文本精准识别、正常中性科技推文防误杀、Grok Prompt 构建与结构化 JSON 解析、持久化防重标识命中跳过、画像打标与排除高危筛选；全仓库单测增至 423 项全量通过。
