## 一、排障背景与用户现象

用户反馈在执行评论追踪自动关注任务时，日志中针对正常活跃账号 `https://x.com/zhangttt12345` 出现报错：
```text
2026/10/16 20:13:25 评论追踪 定时执行 未成功
@zhangttt12345
Cannot find specified user.
扫描主页帖子（共 5 条）：...
```
而在 15 秒后的下一条记录中，另一个账号 `@K1023L` 报出了：
```text
2026/10/16 20:13:40 评论追踪 定时执行 未成功
@K1023L
Rate limit exceeded
```
**用户疑惑**：`@zhangttt12345` 明明是一个完全正常的未关注账号，且已正常扫描到了 5 条帖子并通过了互粉意向评估，为什么扩展却报错“找不到该用户”？是否因为紧接着被限流而误报？

---

## 二、根本原因定位

排查表明：**该报错与限流无关，根本原因是评论解析逻辑将“推文 Snowflake ID”误存为了“用户 rest_id”，并在发起关注时作为 user_id 发送给了 X 官方接口**。

### 2.1 评论采集阶段的 ID 错位
在 `network-api.js` 的 `parseTweetReplies` 中解析 TweetDetail 时间线回复时：
```javascript
// 错误旧代码：
const id = String(tweet.rest_id || legacy.id_str || ''); // 此处 id 是推文自身的 ID
replies.set(id, {
  id, // 将推文 ID 赋给了 reply.id
  handle,
  ...
  replyId: id,
});
```
随后在 `mergeCommentTracking` 聚合评论者数据时：
```javascript
// 错误旧代码：
current.id = reply.id || current.id; // 直接把推文 ID 赋给了用户对象的 id
```
导致存储在 `commentTracking.users` 中的每个用户，其 `user.id` 实际记录的都是该用户发表的那条评论推文的 Snowflake ID。

### 2.2 定时关注阶段的参数调用
在 `background.js` 的 `runCommentAutoFollow` 中：
```javascript
if (user.id) {
  const result = await networkFollow(tabId, user.id);
  ...
}
```
`networkFollow` 向 X 关注接口 `POST /i/api/1.1/friendships/create.json` 发送请求体：
`user_id=<推文ID>&skip_status=true`

X 后端在根据 `user_id` 检索用户表时，自然找不到任何匹配的用户，因此直接返回 Twitter 官方错误码 **108**：
```json
{"errors":[{"code":108,"message":"Cannot find specified user."}]}
```

### 2.3 缺少降级重试逻辑
旧逻辑中假定 `user.id` 只要存在就绝对可靠。当 `networkFollow` 报错时，未对非限流错误（如 108）做进一步处理，而是直接将用户置为失败，没有尝试通过 `UserByScreenName` 重新查询真实用户 ID。

随后 15 秒处理 `@K1023L` 时，由于该账号尝试发起正常关注请求，才真正触发了 X 官方的关注频率限制（HTTP 429 `Rate limit exceeded`）。

## 三、架构改造与代码修复

针对以上缺陷，进行了从“数据解析”、“存储清洗”、“接口兼容”到“自动容错重试”的四重保障改造：

### 3.1 准确提取用户 rest_id 并清洗旧数据
- 在 `network-api.js` 中新增真实用户数字 ID 提取：
  ```javascript
  const userId = String(user.rest_id || userLegacy.id_str || user.id_str || (user.id && !String(user.id).startsWith('VXNl') ? user.id : '') || '');
  ```
- 在 `mergeCommentTracking` 与 `collectTweetReplies` 中严格使用 `reply.userId` 赋值，自动丢弃和纠正旧存储中残留的推文 ID。

### 3.2 关注接口双参数兼容
- 重构 `networkFollow` 和 `networkUnfollow`，支持传入 `{id, handle}` 对象：
  ```javascript
  const id = typeof target === 'object' ? (target?.id || target?.userId) : target;
  const screenName = typeof target === 'object' ? (target?.handle || target?.screen_name) : '';
  const params = {skip_status:'true'};
  if (id) params.user_id = String(id);
  if (screenName) params.screen_name = String(screenName).replace(/^@/, '');
  ```

### 3.3 自动降级与自我修复机制
- 在 `background.js` 中，当直接使用 `user.id` 关注失败且非限流状态（如遭遇 108 找不到用户）时，后台自动触发自我修复：
  1. 调用 `UserByScreenName` 实时查询目标 handle 在 X 上的官方真实 rest_id；
  2. 将纠正后的真实 ID 立即持久化回 `user.id`；
  3. 使用纠正后的 ID 重新调用 `networkFollow` 发起关注；
  4. 若此时已经处于已关注状态，则直接完成流程。

   - **X 接口返回 HTTP 200 OK**，成功返回用户信息；
