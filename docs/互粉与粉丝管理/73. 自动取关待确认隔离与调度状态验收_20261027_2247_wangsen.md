# 自动取关待确认隔离与调度状态验收

- 时间：2026-10-27 22:47，Asia/Shanghai
- 本地版本：3.7.1；正式发行仍为 3.2.7，未提交、推送或发行。
- 需求：一个账号的操作结果待确认不能卡住其他账号；排队、全局暂停及恢复条件可见；按用户实际任务验收。

## 问题与产品边界

原逻辑只保留一个 `state.pending`。每次启动先核验它，结果不符合成功条件就抛错退出，导致后续账号一直无法处理。旧测试将整轮停止作为预期，单测全绿不能证明用户任务得到完成。

待确认操作必须保护该账号，不能盲目重发；登录账号不符、平台限流、网络整体异常等仍应停止当前轮。未知目标身份且无法安全隔离的损坏记录继续阻止操作，不能猜测放行。

## 实现

1. 将旧单条 pending 原样迁入当前绑定账号的 `pendingItems`，保留请求时间、目标、操作类型与已用额度。
2. 账号 ID 或 handle 任一匹配待确认目标，都不再进入可执行队列，避免改名或用户名复用导致重复操作。
3. 每轮最多自动核验一个待确认账号，间隔至少 10 分钟，每条最多 3 次；达到上限继续保留保护，其他账号继续推进。
4. “核验”仅检查已有关系并回写确认结果，不发送新的关注或取关请求。仅允许管理面板发起。人工核验未知 handle 也不会落入普通执行分支。
5. 普通操作仍遵守每天额度、每轮最多 1 人、最小 1 分钟间隔、执行时段、豁免、白名单与登录身份核验。
6. 持久化本轮状态及原因；面板依据当前设置、账户额度和实际 alarm 显示执行状态、恢复条件和下次检查时间。此时间是下一轮检查时间，不是某个账号的预计完成时间。
7. 每行账号名下显示“排队第 N 位”“待确认 · 已隔离”或“待入队核验”；提示支持键盘聚焦。待确认列表可展开并逐条核验。
8. 修复账号级 pending 清除后的列表刷新，迁入隔离列表不冒充成功。状态刷新保留行数据，避免待入队提示被定时刷新清空。
9. 窄屏下保留表格可滚动高度；调度状态区有高度上限，避免展开待确认列表后挤掉账号表格。
10. 主页核验与操作最多等待 60 秒，超时关闭该操作创建的临时标签；迟到脚本结果不能推进至下一次点击。已尝试提交的操作继续待确认，明确尚未点击的操作返回未操作。上一轮运行中再次收到 alarm 时保留下次计划，避免闹钟消耗后丢失后续调度。

主要文件：`src/features/relationships/auto-unfollow.js`、`auto-unfollow-state.js`、`auto-unfollow-view.js`，以及 `AutoUnfollowStatus.vue`、`useAutoUnfollowStatus.js`、`followback-live-refresh.js`。

## 复用评估

沿用项目现有持久化状态和 Chrome alarms，不增加通用调度框架。[p-queue](https://github.com/sindresorhus/p-queue) 提供进程内 Promise 并发与超时管理，不能替代扩展 worker 重启后的状态恢复和账号级操作不确定性判定。[Chrome alarms 官方文档](https://developer.chrome.com/docs/extensions/reference/api/alarms)提供后台计划机制。本次代码只补足业务隔离、核验上限和状态展示。

本次最有证据支持的根因是验收重载中断了正在执行的页面操作，不能将其描述为该账号无法取关或 X 明确拒绝。此前只依据持续未返回的状态推测页面加载卡住，证据不足；应以本次时间线纠正。

旧实现只在调用 unfollow 前写 pending，返回后才记录结果；浏览器中断时没有持久化“已打开页面、已点首层按钮、已点最终确认”等阶段。因此无法事后证明最终确认是否点击，也没有 HTTP 拒绝码可归因。当前 following=true 不是历史请求从未发出的证明，不能据此清空 pending 或自动重发。

后续验收重载必须避开正在运行的轮次及临近的 alarm；旧的间隔采样后直接 runtime.reload 的临时验收脚本不得复用。该记录保留原始历史与额度，本轮仅进行读取与复盘，没有重新取关。
