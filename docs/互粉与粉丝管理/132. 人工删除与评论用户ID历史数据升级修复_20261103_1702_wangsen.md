## 问题与证据

回关监控人工审核中的“本地账号身份已变化，未删除”并非登录账号变化。账号模块的当前账号、关注队列绑定及自动取关设置均为同一个账号。错误来自本地删除把各来源的用户 ID 与人工审核记录的 ID 比较。

五条历史审核记录的 `user.id` 与 `commentTracking.users[].sources[].replies[].replyId` 完全相同。评论 ID 曾被当作用户 ID 传播到跟进派生记录。另有资料缓存和互关网络保存了正确的用户 ID，因此触发冲突。新采集解析已区分评论 ID 与 `userId`，但历史记录尚需统一升级修复。

## 处理规则

人工明确确认“删除本地记录”后，以所属账号、规范化 handle 和审核记录快照确定删除范围。保留账号归属及审核版本检查；不同来源的历史 ID 不再阻止删除。日志和其他所属账号的记录保留。删除仅作用于本地，不调用 X 关注、取关或移除关注者接口；重新采集仍可创建新记录。

历史修复仅认可“用户 ID 与保存的评论 replyId 完全一致”的证据，不凭 Snowflake 长度或时间猜测类型。按相同 handle 与相同所属账号查找可信资料：存在唯一可靠用户 ID 时替换；缺失或冲突时清空已证实错误的 ID，留待后续获取资料。帖子 ID、原始评论 ID、内容和历史日志不变。

同样纠正回关监控审核记录的错误引用，保留人工审核或跳过选择、原尝试次数、额度、调度队列。已有外部操作结果不明确的凭据保持原样，不因迁移重新提交操作。

## 版本升级入口与恢复

复用现有记录库及持久增量日志。记录库第一次就绪访问自动执行 `replyUserIdRepair` 数据升级，完成前不向调度器返回业务数据。旧库已完成归档迁移也会执行；首次归档或从持久备份重建同样执行。不是针对当前机器的 CDP 数据修改。

修复逐条通过原有备份日志写入，并保留 `userIdRepair` 原值审计。全部完成后写入版本化完成标记。中断后恢复未完成日志并通过审计证据续跑；重复打开不会重复修复。所有用户加载包含此修复的版本后会走同一入口，无需手动运行脚本。

未把跨 IndexedDB 和 chrome.storage 的业务恢复塞进 Dexie schema 事务：已复用项目现有备份、串行写入、恢复机制，避免绕过持久日志或另建迁移框架。Dexie 的 schema upgrade 只适合同数据库事务，不覆盖本轮跨存储恢复要求。
