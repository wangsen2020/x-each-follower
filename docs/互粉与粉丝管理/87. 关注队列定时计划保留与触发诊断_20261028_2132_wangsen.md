## 已确认的代码缺口

1. 原 schedule 默认清除现有 alarm 并重新等待完整间隔；手动入队和保存非时间设置也调用此路径，可持续推迟原计划。
2. 原计划只存在于 Chrome alarm 中；alarm 丢失后，后台恢复会重新等待完整间隔，没有已到期计划可恢复。
3. 调度入口、准备主页和同步候选阶段没有持久状态，后台重启后只剩“尚未执行调度”，不足以定位前置阶段中断。

## 实施

- 继续使用 Chrome 原生 alarms，参考官方 alarms 文档和扩展示例，不引入页面计时调度库。普通网页调度库不能承担 MV3 后台唤醒；仅增加保存业务计划的最小适配层。
- queue-alarm-plan.js 序列化计划读写，在 followQueueSchedule 保存账号、下次执行时间、变更原因和最近阶段。首次接入采用现有 alarm 时间；alarm 缺失时按原时间恢复，包括已过期的时间。
- 入队、普通设置保存和后台恢复保留时间。重新启用、修改 every 或 jitter，以及一轮结束后才重新排期；关闭时清除 alarm 与持久到期时间。
- 调度入口在候选同步之前写 dispatch-start 执行日志，并保存 bootstrap、sync-candidates、run-queue、reflect-results 和 idle 阶段。
- 列表接口返回持久 nextRunAt，复用面板已有“下次计划”展示。
- 版本元数据与 README 同步到 4.0.1 开发版本，公开发行链接仍指向实际 4.0.0。

## 中断任务启动前归档与恢复

按用户补充要求，新增 recoverInterrupted，在新批次启动、同步候选及领取任务之前执行。依据后台单实例及调度器 owner 区分新旧执行器，仅恢复当前绑定账号中由旧 owner 遗留的 running 项；当前 owner 的占用和其他账号均不触碰。

归档与状态恢复位于同一 IndexedDB 事务：meta 保存原任务检查点、旧 owner、恢复时间和恢复后状态。释放旧 lease 后，未发出操作的转 pending 并立即允许领取，确认成功的转 followed，已尝试关注、移除或生成发布但结果不明的转 uncertain。原结果与评价保留，旧 owner 的迟到 settle 因 lease 不匹配被拒绝。恢复逐项写执行日志，再开始新批次。

新增回归覆盖未到期旧 lease 恢复、读取阶段待处理恢复、已尝试操作待核实、已成功结果保留、当前 owner 保护、跨账号隔离、重复恢复幂等、迟到写入拒绝和归档记录存在。npm test 1338 项全部通过，源码检查和 dist 构建校验通过。未主动重载当前正在使用的插件，真实中断后恢复尚需加载本次构建后验收。
