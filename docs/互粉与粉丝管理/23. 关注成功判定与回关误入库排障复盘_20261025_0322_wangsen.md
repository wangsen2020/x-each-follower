# 关注成功判定与回关误入库排障复盘

创建时间：2026-10-25 03:22，作者：wangsen。状态：本地修复与验收完成，未推送、未发行。

## 问题与证据

未回关列表把部分实际上未关注的账号当成“已关注”。旧 `autoFollowLogs` 有“关注成功”记录，但那只能说明当时程序走到了成功分支，不能证明 X 后来的关系状态。旧 `profileCache` 中的 `following:false` 也可能早于关注动作，不能单独用于批量删除。

在已登录的 XFollower CDP 浏览器里，用本轮创建的非激活页面读取账号资料按钮并比对用户 ID：`EastgoCC`、`Ericjessss`、`elaineguyue`、`fireandstart`、`ferryu111` 当前均显示“关注”，ID 与本地记录一致。其中 `ferryu111` 已改名，页面显示 `@FerrYu111`，仍由同一用户 ID 确认。`danielj_real` 显示“正在关注”，因此保留。未据旧缓存推断其他账号的当前状态。

## 根因

1. 关注接口的 HTTP 2xx 被直接当成关注成功，随后写入监控与队列；接口响应未必证明目标关系已变为 `following:true`。
2. 回关监控和关系投影会从旧 `monitor.followingUsers`、`followedAt`、旧队列成功标记推断仍在关注；明确的 `following:false` 可能被覆盖或重新导入。
3. 回关检测从旧监控列表和跟踪记录构建主动关注集合，形成误标回流。关系扫描原有的增量合并也不会自动清掉旧集合中已经不在完整列表里的账号；本轮对有实时 X 证据的历史记录做定向修复，完整列表扫描的自动清理留待独立处理。

## 修复边界

- 关注请求成功后核对返回的目标用户 ID 与关系；没有可确认的 `following:true` 时按结果待核实处理，避免触发监控入库及自动二次关注。
- 旧日期、旧 `autoFollowState` 和旧队列成功结果不再单独证明当前已关注；明确的 `following:false` 优先于旧集合推断。
- 回关监控只接收当前关注候选，已标记未关注或已取关的历史跟踪项不能被旧列表重新送回检测。
- 当前未关注的五位账号：通过记录接口移除错误的 `monitor.followingUsers` 行，修正 `mutualNetwork` 和 `unreciprocatedTracker` 的关系及状态，清除错误关注日期；另把关注队列的任务和去重结果改为“待核实”。旧操作日志保留供追溯。修复前记录备份保存在本机 `C:\jtmp\xfollower-followback-20261025\`，不进入仓库。

## 验收

- 上述五位在 X 页面核对后才修复；`danielj_real` 当前关注关系未改动。
- 已复读记录投影与关注队列：五位误标账号的监控来源及派生“未互关”记录消失，关系档案与跟踪状态不再显示已关注，任务及去重结果均为“待核实”。阿喵的已关注记录保留。

- Antigravity 审查指出跨集合旧关注列表仍可能覆盖其他集合的显式未关注，以及 `no_longer_following` 状态遗漏；已加入共同的冲突过滤规则和对应回归测试。它指出旧测试仍期待“队列成功即已关注”，该期待与本次确认规则冲突，已按新语义更新测试。

## 限制

本轮定向修复仅覆盖已核实身份与实时关系的账号。其他历史条目若缺少当前 X 证据，保留待核实，不按旧缓存批量改写。新代码已完成源码测试和隔离构建，尚未替换共享 Chrome 当前加载的扩展版本，因此本轮实机证据对应历史数据修复，新的关注请求判定尚未在真实账号上执行关注动作验收。
