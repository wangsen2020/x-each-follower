# 取关历史独立保存与缺 ID 核实调度修复

- 分支：feature/fan-review-flow；开发版本：4.30.0，未提交、未发行。
- 复用现有 Dexie 投影、增量日志与备份恢复，不引入第二套存储基础设施。

## 根因与现场证据

已取关列表依赖活跃账号的 tracker 记录。无关系清理同时删除 tracker，导致历史统计从较大的值下降到 22。当前成功日志有 732 个唯一账号，其中 720 个不在现存列表，且均有 no_relationship 清理标记。日志中曾记录“已经取关 791”，但现有可验证的成功明细不足以保证恢复到用户记忆中的全部数量；不能将全部清理对象当成取关成功。

核实 alarm 每分钟正常唤醒，调度 nextAt 正常前移，却长期 total 为 0。待核实的 9 个历史账号缺少 X 用户 ID，automaticCandidates 在进入核实前要求 ID，造成补齐 ID 的任务反而被 ID 门槛拦住。

## 实现

1. 在 unreciprocatedTracker 的独立根元数据中维护 unfollowHistory，按归属账号与用户名去重，保留最新成功时间及证据来源。历史不依赖用户资料行，不参与关注关系或业务队列。
2. 首次读取升级及后续后台启动从分页成功日志增量恢复，仅接纳 result=success 且明确列出 unfollowedHandles 的记录；现存 status=unfollowed 且有有效时间的 tracker 同样纳入。失败、泛化成功、单纯删除记录均不能算作取关成功。
3. 新的取关成功写入 tracker 时同步持久保存历史；通过现有 mergeRoot 增量日志备份，升级中断可重试，重建数据库可恢复。升级游标只在恢复步骤完成后写入。
4. 已取关列表与计数读取独立历史，并与兼容旧记录去重。无关系清理、人工删除本地资料均不删除成功历史。其他账号历史隔离，旧数据使用已有归属绑定。
5. 待核实允许有用户名、没有 X 用户 ID 的记录进入现有只读资料核实器；取得 ID 后继续原有审核链路。仍保留明确 ID 冲突与不确定写入的保护。
6. 无 ID 任务以 handle 为退避键，每个账号独立记录尝试时间，防止空 ID 共用冷却。沿用原有访问预算，不增加频率、不绕过限流。
