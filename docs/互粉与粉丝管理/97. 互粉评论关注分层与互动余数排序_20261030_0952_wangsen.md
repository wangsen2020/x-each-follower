# 互粉评论关注分层与互动余数排序

本轮为已有排序优化，版本 4.7.1，分支 feature/mutual-comment-priority，基于 develop 的 5e886fc，通过 git flow feature start 创建。

## 排序规则

仅已持久化互关标签（tag、taggedAt、tagBatchId 完整）、处于待评论/生成中/待发布且无装饰文案阻塞的帖子参与待评论排序。

明确未关注作者的帖子：权重 = 1000 + 综合分 % 1000。综合分复用 postEngagementScore，为评论×1 + 转发×3 + 点赞×3 + 收藏×3。其他帖子权重为 0；关注未知或字段冲突不推断为未关注。互动数缺失/无效时只保留基础分。

取余严格按需求，例如 999→1999，1000→1000，1200→1200，并非综合分越高权重必然越高。同权重沿用尝试时间升序、采集时间降序，再以帖子 ID 稳定排序。列表先全量排序后分页，后台使用同一比较器；重试时间、每日限额、发送间隔、账号核实仍生效。高权重任务持续到达时，低权重任务可能延后。

## 数据与界面

home-reader.js 从首页接口读取作者关注状态和四项互动数。store.js 对重复帖子仅刷新这些观测字段，保留标签、创建时间、AI任务、草稿、发布凭据和历史；作者 ID 冲突不更新。旧数据不会凭空补齐，需后续采集重新遇到对应帖子。关注状态代表最近一次采集的快照，不是执行前实时关系核验。

runtime.js 将同一权重提供给列表和调度；MutualCommentsSection.vue 在待处理状态下显示权重、关注状态及公式提示。

已评估 Lodash 的通用排序能力（https://github.com/lodash/lodash ，https://lodash.com/docs/）；现有原生排序及项目综合分函数已覆盖需求，无需增加依赖。业务差异仅包含分层、取余及比较规则，不重建通用调度或存储设施。

## 验收反馈：采集提示 must be defined

用户报告同一提示再次出现。历史扫描记录在4.7.0已有多次同文失败，夹杂成功扫描。只读复现确认首屏成功、分页请求抛出该错误；原始失败未保存完整HTTP响应，因此不能将模板竞争断言为所有历史失败的确定根因。

针对代码中当前首屏与全局模板分离的风险，net-hook将原生首屏响应与请求模板一起保存；扫描将该模板传给现有网络客户端，固定本轮queryId、variables、features和fieldToggles。旧页面无快照时兼容原缓存路径。分页失败补充页码、操作及HTTP状态，HTTP200但包含接口错误也不再误判成功。未简单清空历史错误。
