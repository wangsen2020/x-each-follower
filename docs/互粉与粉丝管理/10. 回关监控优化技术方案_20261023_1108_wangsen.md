## 1. 目标与术语

将全站用户可见名称“回关监测”统一为“回关监控”。本模块回答：**我们正在关注哪些人，其中哪些人目前没有关注我们，以及等待了多久、是否曾经互关。**

设 F 为本账号当前粉丝集合，G 为本账号当前关注集合：

| 概念 | 集合或条件 | 所属功能与动作 |
| --- | --- | --- |
| 未回关 | G − F：我们关注了对方，对方没有关注我们 | 回关监控；查看、保留关注或取关 |
| 待回关 | F − G：对方关注了我们，我们没有关注对方 | 粉丝管理与统一关注队列；由我们回关 |
| 已互关 | G ∩ F | 回关监控的已互关视图 |
| 曾互关后未回关 | 当前属于 G − F，历史存在可信互关证据 | 未回关的关系变化标签；发现时间不是实际取关时间 |
| 超时 | 当前未回关，且已知本次关注起点，经过时长达到配置阈值 | 独立状态列及筛选条件，不作为关系分类 |

“未回关”和“待回关”方向相反，不能共用用户文案、统计口径或自动入队条件。回关监控内移除“待回关”标签页；缓冲期内也叫“未回关”，期限状态显示“未超时”。

本地比较无需打开 x.com。必须同时拥有本地关注集合和粉丝集合；只看粉丝集合本身无法枚举不在其中的已关注账号。复用粉丝管理已保存的两类数据即可，不需要再逐人访问主页。

## 2. 现有实现核查

以下为本次源码阅读结论，未进行浏览器运行验收：

| 位置 | 当前行为 | 优化要求 |
| --- | --- | --- |
| `src/entries/panel/pages/UnreciprocatedSection.vue` | 首个标签为“超时未回关”，另有“待回关/已回关/全部” | 改为“未回关/已互关/全部关注”，期限状态独立列 |

| `src/features/relationships/relationship-rules.js` | 主要按 handle 建索引；多个派生规则缺少完整性证据 | 使用账号隔离和稳定用户 ID，统一纯规则，未知不等于 false |
| `src/entries/background/background.js` 闹钟 | 通知面板执行；无面板时发提醒 | 本地重算转入后台，不要求管理面板或 X 页面打开 |
| 设置与批量取关 | 已有期限、白名单、批次、间隔、停止等能力；自动与手动路径各自处理 | 复用既有能力，统一入口执行保护，补齐日志和恢复 |

这里的“完整模块加载”只说明本地数据库记录读全，**不代表已完整同步 X 的当前名单**。累积档案也不能直接当作当前粉丝集合，否则别人取关后仍可能留在粉丝索引里。

## 3. 参考项目的可借鉴能力与边界

研究对象：[lonly2010/x-mutual-checker](https://github.com/lonly2010/x-mutual-checker)，核查时间 2026-10-23；本次读取代码固定于提交 `593d918330035b58dc825b66c60eb00e95d6b9bc`。

源码依据：[content.js](https://github.com/lonly2010/x-mutual-checker/blob/593d918330035b58dc825b66c60eb00e95d6b9bc/x-mutual-checker/content.js)。README 介绍其列表读取、界面、历史对比及后台兜底分工；本次重点核对 `applyScan`、列表筛选、忽略和 CSV 逻辑，未安装运行参考插件。

| 参考能力 | 本项目采用方式 |
| --- | --- |
| 区分全部未回关与曾互关后取关 | 未回关完整覆盖 G − F；“曾互关”作为标签及快捷筛选 |
| 首次保存互关基线，后续判断变化 | 无基线时只报告当前关系，不能声称对方历史上取关过我们 |
| 保存 discovered/detected 时间，重新关注后移除当前告警 | 保存事件历史，当前列表按最新关系恢复，重复重算不重复创建事件 |
| 蓝V筛选、搜索、粉丝数排序 | 默认展示全部未回关，蓝V作为可选筛选，避免隐藏普通账号 |
| 忽略、结果本地持久化、CSV | 引入可恢复的“保留关注”保护名单，导出当前筛选结果并带证据时间 |
| 部分扫描保留未读到的历史数据，完整扫描才清理部分失效结果 | 采用扫描批次与完整性门槛，明确本地档案与当前成员关系 |
| 单个/批量取关，可停止 | 统一执行通道、状态校验、停止和结果记录 |

不照搬的规则：参考代码在读取至少 20 人且互关数为零时拒绝保存，这是启发式保护，不足以证明解析失败；本项目应检查字段有效性、扫描完成状态和证据冲突。参考界面把部分异常描述为“不是主动取关”，但关注数为零不能单独证明动机。本项目只标记“账号异常/待核实”，不推断恶意、欺骗或主动取关原因。参考项目的扫描速度及取关间隔不作为本项目性能保证或安全保证。

## 4. 页面设计——按本次截图调整

### 4.1 列表与统计

- 默认标签：**未回关**，包含未超时、已超时、关注时间未知的所有有效 G − F 记录，不受 14 天限制。
- 其他标签：**已互关、全部关注**。数据不足的记录在全部关注中显示“关系待确认”，另提供快捷筛选。
- 未回关视图筛选：期限状态、曾互关、蓝V、保留关注、关键词。各筛选叠加作用于完整数据集。
- 侧栏角标显示未回关总数，不再只显示超时人数；保护账号仍计入关系总数。默认列表可隐藏保护账号，但必须展示“保留 N”及查看入口，不能静默减少总数。
- 主表列：选择、账号与简介、关注时间、等待时长、期限状态、关系变化、粉丝、关注、操作。窄屏可将关注时间与等待时长合并为一列两行。
- 期限状态仅为“未超时 / 已超时 / 时间未知”；关系变化为“曾互关 / 未记录互关历史”，不把后者称为“从未回关”。
- 默认按等待时长倒序，即已知 followedAt 从早到晚；未知时间排最后。同值以稳定用户 ID 排序，分页之前在完整集合排序。已互关视图不继续累计等待时长。
- 未回关标签为空时显示“暂无未回关账号”；数据不足时显示“本地名单尚未完整”，不得用空列表伪装为检测成功。

### 4.2 操作与布局

- “开始检测”改为“重新比对”，只读取本地数据、计算和保存结果；不触发取关、不开 X、不获取主页、不调用 Grok。
- 独立“同步名单”入口复用粉丝管理同步任务，可跳转其进度；同步是联网动作，不能藏在重新比对内。
- “取关全部超时”改为“选择超时账号”，明确作用范围和数量，然后由批量取关执行；全选当前页与选择全部匹配结果必须区分。
- 保留单个取关、批量取关、停止、保留关注/取消保留、CSV 导出、执行日志入口。
- “每页”标签与下拉框间距严格为 `margin-right:10px`；常规输入/按钮/下拉框高 30px、字号 12px，相邻控件间距 10px，最后一项不留右间距。
- 解释放入可键盘聚焦的圆圈问号，保留短标签；圆圈 14px、填充 #769287、白色 Arial 10px 粗体问号。窄屏和翻译后允许自然换行，不裁切。
- 状态栏分开显示“名单更新时间”和“本地比对时间”；点击重算不能刷新名单更新时间。去除“无信用、浑水摸鱼、自动安全取关”等无法由关系事实推出的描述。

## 5. 本地关系数据与计算规则

### 5.1 复用存储，补齐证据

复用现有 records / IndexedDB 数据层，不另建一套粉丝档案。新增的关系快照和事件记录也通过现有 repository、projection 和迁移流程管理。

建议数据字段：

| 对象 | 主要字段与用途 |
| --- | --- |
| 名单批次 | ownerAccountId、scanId、kind、startedAt、completedAt、coverage、source、cursor、revision；coverage 区分 partial/complete/failed |
| 关系证据 | ownerAccountId + targetUserId、following、followedBy、observedAt、source、scanId；两个方向允许 unknown |
| 关注区间 | followingSince、followingSinceSource、firstObservedFollowingAt、endedAt；真实关注时间与首次发现时间分开 |
| 互关事件 | eventId、targetUserId、type、detectedAt、evidenceRevision；保留曾互关、失去互关、恢复互关历史 |
| 用户保护 | targetUserId、protected、reason、updatedAt；与关系分类正交 |

以 X User Rest ID 为主键，不把 Tweet ID 当用户 ID；handle 只作展示和兼容回退。旧记录缺 ID 时规范化 handle 并标记身份待补全，出现冲突不得跨账号强行合并。ownerAccountId 必须进入读取、缓存、事件和动作键，切号不混用。

### 5.2 当前集合的维护

1. 分页同步以 scanId 累积本轮观测；未完成时保留已有可信快照，不能因本页没有某人就认定其取关。
2. 完整一轮成功结束，才发布新的当前成员集合；保留档案资料，更新成员关系，不删除用户画像。
3. 粉丝和关注两边独立记录完成时间及版本；读取某次固定版本组合计算，避免计算中途混入另一批数据。
4. 当前 G 中的账号，有可信 F 成员证据则为互关；在完整 F 中缺席才可由差集判未回关。若具有时间和来源明确的 followedBy=false，也可直接作为否定证据。
5. 较新明确关系证据优先于旧证据；时间顺序无法确定或同一版本矛盾时标记待确认。新证据不得被旧 followedBy=true 的 OR 条件覆盖。
6. 数据缺失、失败、部分结果、来源过旧时展示相应状态及历史结果时间；禁止据此新建“对方取关”事件或执行自动取关。
7. 检测结果准确性以数据覆盖为边界；不为得到实时结果暗中打开 X。名单更新完成后触发一次本地重算。

### 5.3 时间与状态

- 可信关注起点来自本工具成功关注事件或可验证的历史记录；导入数据无时间时保存 null，不用导入时间假冒关注时间。
- 未回关无需关注时间也可列出；未知时间不能自动判超时，可显示首次发现时间作为辅助信息。
- 超时使用精确毫秒差值与阈值比较，等待天数仅负责显示；默认沿用 14 天，配置改变后离线重算。
- 先确认当前 following=true，再判断回关和超时；已取消关注的账号退出当前关注集合，但历史事件保留。
- 再次关注形成新的关注区间，不能复用最早关注时间导致立即超时。
- 重新互关后解除当前未回关/超时状态、清除待执行取关候选，保留历史变化记录。
- “曾互关后未回关”要求此前互关证据与当前明确未回关证据；发现时间只代表系统发现的时刻。

## 6. 模块拆分与调度

建议在 `src/features/relationships/` 新增纯计算模块，例如 `followback-monitor.js`，统一返回关系分类、期限状态、证据状态和排序键。具体文件名在实施时结合现有架构确定。

```text
粉丝管理同步 / 已确认的关注与取关结果
                    ↓
现有 records 存储 + 名单批次与关系证据
                    ↓
后台本地重算服务 → 结果投影、统计、事件
                    ↓
回关监控界面 → 用户选择 → 独立取关执行器
```

- UI、侧栏数量、records 投影、后台闹钟共享同一套规则，避免 panel 和 relationship-rules 再次分叉。
- 本地重算服务不依赖 DOM、tabs、network-api 或 Grok，支持无 X 标签页、管理面板关闭时执行。
- 同一 owner 的任务串行或合并；重算以输入 revision 和规则版本幂等提交。并发更新时丢弃旧计算结果并重算。
- 现有闹钟保留为本地期限状态刷新；名单刷新沿用粉丝管理调度。不要为回关监控另起全量抓取器。
- 未回关只供监控和取关候选；待回关自动入统一关注队列的条件仍是 F − G，经现有风险筛选后入队。两条链路不得相互误投递。

## 7. 取关与保护规则

1. “重新比对”始终无外部动作。自动取关即使启用，也由独立任务消费明确候选，不与检测按钮串联。
2. 保留关注名单是强保护，统一作用于单个、批量、选择全部超时及自动路径。只有明确取消保护后才可选为取关对象。
3. 手动批量执行前展示实际数量和范围，排除保护、已互关、已取关、关系待确认记录；自动路径额外要求已超时且时间可信。
4. 执行前检查当前账号、最新关系版本与保护状态；证据过期或矛盾则跳过并提示同步。联网会话需要时由执行器取得，不影响离线查看与比对。
5. 手动与自动使用同一批次上限、间隔、停止机制和动作锁；鉴权失败、限流或连续失败应停止本批。随机等待不承诺避免风控。
6. 请求失败或响应不明确不能直接写成已取关；标记结果待核实，禁止无依据重复执行。确认成功才更新各模块的当前 following 状态。
7. 记录计划数、实际成功、跳过原因、失败、待核实和停止位置。浏览器重启不得自动重放结果不明的动作。
8. 新安装自动取关默认关闭；迁移旧版已开启设置时展示“需重新启用”的迁移提示，待用户按新候选规则启用，避免新名单扩大后立即批量执行。

### 7.1 设置分组与建议默认值

以下数值是产品方案建议值，尚未启用，不是 X 官方额度或安全阈值。界面分为“等待期限”“自动取关”“首次私信提醒”三组；本地监控、自动取关、首次私信提醒分别开关，开启监控不隐含开启后两项。这里的私信目标是“我们关注对方、对方尚未关注我们”的未回关账号，不是“对方关注我们、等待我们回关”的账号。

| 分组 | 配置项 | 建议默认值及可配置范围 | 规则 |
| --- | --- | --- | --- |
| 等待期限 | 最长等待回关时间 | 14 天；1–90 天 | 从本次可信关注起点计算；达到期限标记已超时，替代原 overdueDays 的重复设置 |
| 等待期限 | 本地比对周期 | 60 分钟；5–1440 分钟 | 仅刷新关系投影和期限，不等于联网同步或取关周期 |
| 自动取关 | 启用自动取关 | 关闭 | 关闭后只标记超时，保留手动操作 |
| 自动取关 | 执行周期 | 30 分钟；5–1440 分钟 | 按两轮开始时间计算；每轮只消费到期且符合保护规则的候选，独立于本地比对周期 |
| 自动取关 | 周期浮动 | ±5 分钟；0–60 分钟 | 小于执行周期；最早执行仍不得早于该账号到期时刻 |
| 自动取关 | 每轮最多 | 20 人；1–50 人 | 与剩余每日额度、有效候选数取最小值，不为凑批次等待 |
| 自动取关 | 每日最多 | 400 人；1–400 人 | 本产品取关入口共享计数，包括手动；执行结果不明的请求保留额度直到对账 |
| 自动取关 | 每次间隔 / 浮动 | 15 秒 / ±5 秒；间隔 3–300 秒、浮动 0–60 秒 | 默认每人间隔 10–20 秒；浮动须小于基准，实际间隔不低于 3 秒；手动批量与自动共用 |
| 自动取关 | 执行时段 | 09:00–21:00，显示所用时区 | 支持全天或自定义跨午夜时段；时段外延后，不积压后集中补跑 |
| 首次私信提醒 | 启用提醒候选 | 关闭 | 只针对当前未回关账号；到时进入待确认队列，不因本地比对而直接发送 |
| 首次私信提醒 | 关注后等待时间 | 24 小时；可配置 1–30 天 | 从本次可信关注时间起算；必须早于最长等待期限；不按自然日午夜计算“第二天” |
| 首次私信提醒 | 每人最多 | 固定 1 条 | 按本账号与目标 User Rest ID 永久去重；重新关注、修改配置、重启不恢复额度 |
| 首次私信提醒 | 私信内容 | 用户填写并预览 | 支持昵称、账号变量；不使用“剩余天数”制造临期催促，不自动生成威胁或承诺 |
| 首次私信提醒 | 发送方式 | 逐人确认 | 到计划时刻提示用户审核；只有对方明确表示愿意通过私信联系且提供退出方式时才可另行评估自动发送 |
| 首次私信提醒 | 未完成时的处理 | 标记待人工处理 | 无法私信、证据不足或结果待核实时不补发；不因此改变超时期限或自动取关规则 |

“最长等待回关时间”是**进入超时状态的期限**，不是保证到点已经取关。实际动作还受开关、每日额度、执行时段、数据新鲜度和保护规则限制。表格增加“下次动作 / 暂停原因”，例如“已超时 · 等待执行时段”；首次私信提醒在单独一列显示，不把未发送私信当作取关阻断条件。

默认取关节奏按一整天的容量配套设计：09:00–21:00 共 12 小时，每 30 分钟一轮、每轮最多 20 人，平均处理能力约 40 人/小时；400 人需要 20 个满批次，约分散在 10 小时内完成。12 小时窗口提供一定余量，但不保证限流、离线或暂停后仍达到上限。每日 400 是用户设定的产品上限，不是执行目标或平台额度；只有 37 个有效候选时，按两轮 20 + 17 人处理，不补凑其他账号。

单个满批次的 19 次等待合计约 3–6 分钟，另加请求耗时，其余时间等待下一轮。下一轮计划以本轮开始时间加周期与浮动计算，不能在批次结束后再机械增加完整周期；若本轮超时仍未结束，禁止并发，结束后重新安排，不连续补跑错过的轮次。配置保存时估算“时段长度 ÷ 周期 × 单轮人数”的处理容量，让用户看出周期、批量和日上限是否协调。缩短时段不自动提高发送速度。

剩余额度不足一批时自动缩小批次，例如当天已用 393 个额度，下一轮最多执行 7 人。额度在请求前原子预占，成功及结果不明保留占用，确认未执行后才释放；并发入口和重启不得绕过 400 上限。达到上限即暂停到下一个额度周期，不在午夜集中补跑。取关额度与首次私信提醒的每人一次去重互不影响。

### 7.2 提醒时间线与配置校验

设本次可信关注时间为 t0、关注后等待时间为 G、最长等待期限为 T：提醒候选时间 R = t0 + G，超时时间 D = t0 + T。默认 G = 24 小时、T = 14 天；关注满 24 小时进入候选，不等到第 14 天才发。保存配置时要求 G < T；若 T ≤ G，提示用户调整或关闭提醒，不静默移动提醒时间。

- 只有仍在关注对方、对方仍未关注我们、关注时间可信、未在保护名单且该目标未曾收到本账号的这类提醒时，才进入候选；关注时间未知时显示“时间待确认”，不自动推算“第二天”。
- R 到达时只生成一条待确认任务。面板关闭或离线期间错过 R，恢复后只显示当前仍有效的一条候选，不补跑多条。对方回关、我们取关、加入保护名单或已超时，候选即失效。
- 用户打开候选后核对目标和正文，逐人确认发送；点击前再次核对关系与收件权限。若用户到 D 时仍未发送，则关闭候选，照常标记超时；提醒不是取关的必经前置条件。
- 修改 G、T 或时区只重算尚未发送的候选时间；历史已确认发送或结果待核实的目标不重新获得一次提醒。缩短期限导致候选失效时，保存前展示受影响人数。

### 7.3 私信执行边界与状态

私信属于独立联网动作。开启提醒候选可以独立于自动取关；自动取关关闭时仍可在关注满配置时间后提示用户确认发送，到期后只标记超时。本次调整方案不代表现在发送私信。

- 当前 `src/features/grok/verification-self-message.js` 仅向本人提醒，不能当作对外私信适配器。可参考 [X 官方 chat-xdk](https://github.com/xdevplatform/chat-xdk) 的加密接口和 [xChat](https://github.com/grinich/xChat) 的网页 Chat 发送确认逻辑；正式接入前仍需核实当前账号会话、收件人限制与发送结果。
- X 的[自动化规则](https://help.x.com/en/rules-and-policies/x-automation)不允许未经请求的自动私信；“每人只发一条”不构成例外。因此默认仅定时生成候选并由用户逐人确认发送，不能按未回关名单自动群发。未来若支持对已明确要求联系的收件人自动发送，须另行核实接收意愿及退出机制。
- 发送前核对当前登录账号、目标 User Rest ID、仍为未回关、未被保护、证据未过期，并核对模板版本。保留关注账号默认也不发催回关私信。
- 私信状态区分：未安排、待确认、已确认发送、失败、结果待核实、无法私信、已取消。仅有“已提交”不足以确认发送；无法确认时不盲目重发。
- 不把“已确认发送”显示为“已读”或“已送达”。对方不允许陌生人私信、拉黑、账号异常等情况按实际证据记录，不持续尝试。
- 回关、我们先取关、保护开启、私信提醒关闭时取消尚未开始的任务。发送中状态变化无法撤回已提交消息，应记录实际结果。
- 回复私信不等于已回关；每个目标最多一条，无后续催回关序列。用户明确选择“不再提醒”后，本账号对该目标持续停止提醒，再次关注也不自动清除该偏好。
- 对曾互关后退出的账号，不重新套用早已结束的关注前提醒窗口；默认转人工处理。未来如需“失去互关后宽限期”，应作为独立策略设计，不能伪造新关注时间。

### 7.4 调度、去重和日志字段

- 继续复用现有后台任务基础设施，为本地比对、提醒、取关设不同任务类型；共享同一账号的外部动作锁，避免提醒与取关同时操作同一目标。
- 私信幂等键建议为 ownerAccountId + targetUserId + firstGreeting；不包含关注区间和配置版本，避免重新关注后再发第二条。
- 持久化 followedAt、plannedAt、reviewedAt、attemptedAt、confirmedSentAt、messageVersion、messageHash、executionStatus、skipReason、resultEvidence。请求前记录占用；结果待核实占用唯一发送名额，恢复后先核实，不重发。
- 设置摘要显示：“最长等待 14 天；09:00–21:00，每 30 分钟处理取关，单轮最多 20 人、每日最多 400 人；关注满 24 小时提示首次私信，每人最多 1 条、逐人确认”。关闭项标为未启用，账号列表显示提醒计划时间与发送状态。
- 日志可分别筛选本地比对、私信、取关，记录触发来源、配置版本、时间线、真实结果及保护/额度/时段等跳过原因。

此前开关带 `disabled`，界面与后台归一化还会强制把 `autoUnfollow` 置为 false，只有参数保存，没有执行链路。本次移除占位限制，使用独立 `x-auto-unfollow` 后台 alarm；面板关闭后仍可运行，Chrome 关闭时不执行，重新运行后恢复计划。默认每 30±5 分钟一轮、每轮最多 20 人、每日最多 400 次自动取关尝试；保留用户已有周期与间隔配置。每日额度按绑定账号和本地日期分别保存，切换账号、重开面板或 worker 重启不会清零。

启用保存时核验并绑定当前登录账号，身份读取最多等待 8 秒，失败不保存启用状态。执行时核对绑定账号 ID 与导航栏当前账号；仅处理超过等待期限且明确单向关注的记录，跳过豁免、白名单、封禁、不存在和关系未知的账号。每次请求前读取最新设置与豁免状态，再查询实时关系；对方已回关或已取关则仅更新本地记录。实际取关走现有 Network `friendships/destroy.json` 接口，并重新查询关系确认结果。

额度与待确认记录在请求前持久化。明确的 4xx 拒绝或未发出的请求会停止本轮；网络异常与服务端异常保留待确认状态，下一轮仅核验该目标，不重复发送不确定请求。已成功的操作同步更新粉丝、互关、评论与监控来源，保留历史关注时间，避免重新入队关注。执行日志独立存储；临界未知结果需要核对目标关系，未确认前不会继续批量操作。

验收覆盖 759 项核心测试、47 项构建测试、源码与浏览器调用契约检查及生产构建。新增测试覆盖时间窗口、白名单、豁免、运行中关闭、实时回关、每日与单轮额度、跨账号及重启计数、限流、模糊结果不重复发送，以及真实记录运行时的回写与重新打开。CDP 实机验证开关可勾选、保存约 402ms、绑定正确账号、alarm 创建、刷新后仍启用，以及关闭后 alarm 取消。验收使用窗口外的计划，无真实取关；完成后恢复原配置并保持自动取关关闭。证据位于 `scratch/auto-unfollow-acceptance.json`。未提交、未推送、未发版。

### 自动私信提醒接入与补发规则 — 2026-10-24

- 到期条件为当前时间减关注时间大于或等于等待天数；默认满 24 小时。第 3 天、第 6 天、超过取关期限的未回关账号仍符合条件，不使用“仅第二天”的时间窗口，也不依赖本次比对是否产生数据变化。有效历史关注时间无需已有来源标签才能到期。
- 新增独立自动私信开关，启用时绑定当前登录账号 ID。后台 `x-auto-greeting` 每 5 分钟检查一次，每轮最多处理 5 个发送任务；关闭管理面板不影响后台计划，需要 Chrome 和绑定账号的已登录 X 页面。开关初始关闭，不把历史手动私信设置静默升级为批量自动发送。
- 发送前重新读取本地状态和实时 X 关系，并再次核验当前账号、收件人 ID。已回关、已取关、封禁、不存在的跳过；关系未知或加载失败不作为账号注销。中英文正文沿用已有默认文案与语种判断。
- `firstGreeting:<ownerId>:<targetId>` 与手动发送共用。先持久化占用记录，再允许实际发送；成功和结果不明均阻止自动重发，重启、改名、反复检测不会清零。保留历史提醒标记，后续手动失败不会覆盖之前成功的事实。明确未提交的失败冷却一小时后可重试；疑似提交绝不自动重试。
- 日志单独标记“自动私信”，包含准备发送、发送成功、失败和待确认，并另记检查汇总，不再把私信结果显示成一般定时检测或误标为执行失败。标准 14px 帮助图标与开关同排，保留紧凑布局。
- 测试：770 项核心、48 项构建测试通过，源码与调用契约检查、生产构建通过。覆盖超过第二天补发、旧日期、封禁/不存在、实时回关、运行中关闭、并发占用、存储失败、重启和模糊结果防重复。
- CDP：无 X 页面时拒绝启用且不保存；使用已有登录态的独立标签后保存成功、后台计划创建、刷新保持启用。验收前核验 2624 条真实记录在 30 天测试阈值下没有可发送对象，实际触发后台 alarm，产生日志“成功 0，跳过 2624，失败 0，待确认 0”，页面正确显示自动私信分类。对授权测试账号 TorbenWetter 的已有成功记录执行一次性占用检查，返回重复拦截；保留原记录，没有再次发送或对历史名单试发。
- 验收后恢复原本地及同步配置，等待天数为 1，新开关仍关闭；仅关闭本次创建的 X 验收标签。启用正式提醒需在设置勾选自动私信并保存。证据为 `scratch/auto-greeting-acceptance.json`、`scratch/auto-greeting-logs.png`、`scratch/auto-greeting-final.png`。未提交、未推送、未发版。
