# 粉丝分类统一与全局检索实机验收

## 范围与基线

本轮处理粉丝跟进分类重叠、数量与列表不一致、搜索范围不明确，以及历史关系记录对关注队列的影响。按用户要求在当前工作区和已有登录环境实施、验收；保留原有未提交修改，不提交、不推送、不发行。运行版本由 3.3.7 更新为 3.3.8。

## 统一关系视图

原始 monitor 的 users、queue、followingUsers 是不同用途的档案，同一账号可能有多条历史记录。旧列表分别读取档案、粉丝队列和衍生未互关列表，因而相互重叠。

复用现有记录投影的索引、分页、汇总、快照及变更回写能力，在独立 fanDirectory 投影中按账号归属和规范化 handle 生成一条展示记录。没有另建 CRUD 或数据库框架；Dexie 与现有投影继续承担存储能力，新增代码只负责本项目的关系证据规则。

| 分类 | 你关注对方 | 对方关注你 |
| --- | --- | --- |
| 已关注 | 是 | 否 |
| 待回关 | 否 | 是 |
| 已互关 | 是 | 是 |
| 无关系 | 否 | 否 |
| 待核实 | 任一方向缺失、证据冲突或身份不一致 | 任一方向缺失、证据冲突或身份不一致 |

三个明确关系分类互斥。待核实有独立入口，无关系账号保留在全局搜索中。源记录和操作历史不因分类修正而删除；分类是最近本地记录的展示，不是持续实时读取 X。

## 证据时序与中断恢复

- 每个关系方向独立选择最新明确证据；同一时点的正反证据不能互相覆盖，列为待核实。
- 新扫描记录完整关系的观察时间；成功关注仅更新“你关注对方”的时间，不把另一方向旧值误标为刚核验。
- 身份核验存在 User Rest ID 冲突时保留待核实，不用历史成功记录推断当前账号身份。
- 原始记录提交时，在同一事务中记录待刷新 handle。若中断发生在源数据提交与分类刷新之间，重启后按检查点重算，避免新分类视图再次滞后。
- 一次性构建和后续增量重算均使用现有投影能力；普通分类页仍通过索引读取 limit+1 行。

## 搜索、计数与操作

搜索按用户确认覆盖全部分类，支持账号、名称、简介。带 @ 的 handle 和 X/Twitter 个人主页链接精确匹配账号，避免误命中别人的简介；普通关键词继续模糊检索。结果按 handle 去重，显示明确关系或待核实原因；匹配数量在全量本地分类视图中计算，分页不会把当前页数量当成总数。点击分类会清空搜索，清空搜索则返回之前的分类。

列表、标签数量、分页总数和侧栏待回关数量使用同一份投影。更新后的页面会替换旧页面副本，避免相同 userKey 的关系变化仍显示旧内容。

每行提供“核验关系”。该操作读取 X 的实际关系并回写各来源记录，不执行关注或取关，也不会重新开启历史跳过任务。历史已关注任务若与当前未关注状态冲突，进入 uncertain，等待人工核对；运行中任务不被此操作中断。核验身份一致后，复用队列存储的既有合并逻辑处理 handle 占位记录与 Rest ID 记录。

## 队列防重复

- 扫描自动入队与后台粉丝来源同步均复用统一分类；缺失、冲突和无关系记录不会因为陈旧粉丝队列标签自动作为待回关导入。
- 已核验后跳过的任务不因后台同步反复重排；未核验历史跳过任务的放行恢复有一次性标记。
- 已完成任务保留完成结果，执行器仍在提交关注前核验实时身份与关系。
- 历史同名不同身份不能仅凭 handle 合并，保留完成历史和待核实状态。

## 实机验收

使用已有 xfollower-cdp-profile；仅在没有 running 关注任务时重载扩展。未触发关注、取关、发帖或私信操作。

- 全局搜索 @0xCryptovia 和 Caaroliinaleiva 的主页链接均只返回一个账号，并正确显示待核实；不存在的词返回 0。

- 界面中搜索 @T11X1，只显示一条待核实记录；点击核验关系后标签与分类数量同步变为已互关。重载后四个账号均保持已互关。
- 连续两次真实来源同步：第一轮合法新增 11 个任务；第二轮新增 0 个，已有状态变更 0、关注尝试时间变化 0、已完成重新排队 0。网络观察期间关注及取关请求均为 0；已解析 User Rest ID 重复任务为 0。
