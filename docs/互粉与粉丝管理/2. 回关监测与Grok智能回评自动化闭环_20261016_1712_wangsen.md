## 一、背景与迭代目标

在完成了粉丝增量检索、四维关系梳理与拟人看帖自动关注（参见 [1. 粉丝增量检索与互粉追踪自动化升级_20261016_1129_wangsen.md](./1.%20粉丝增量检索与互粉追踪自动化升级_20261016_1129_wangsen.md)）后，我们在真实运营与自动化链路中面临两大关键痛点：

1. **单向骗关与资产贬值**：主动关注的目标账号中，部分用户长期不回关，持续占用单向关注配额，需要建立自动化的**回关监测与超期淘汰机制**；
2. **机械关注转化率低与回评断环**：单向关注易被忽略，若能在关注前后借助自带 Grok 针对博主近期推文发表真实、高情商的互动评论，可大幅提高回关意愿。此前的回评链路存在平台误报拦截、缺少独立模块解耦、以及推文发表未实现端到端真实校验等问题。

为此，本阶段完成了回关监测体系搭建、Codex UI 统一对齐、Grok 回评架构重构、双平台智能降级与推文真实发表的全链路闭环。

## 二、回关监测机制与全模块协同（v0.25.0 ~ v0.25.1）

### 2.1 回关监测系统（Unreciprocated Tracker）
- **双周超期智能判定**：
  - 基于通用关注记录中的 `followedAt`（我方主动关注时间戳）与 `followBackAt`（对方回关时间戳），定时拉取当前粉丝数据进行交叉核验。
  - 若已关注时间超过预设阈值（默认 14 天 / 2 周），且对方仍未回关我方，系统将其精准归类为“超期未回关”账号。
- **独立设置抽屉与定时调度**：
  - 复用互关追踪的设计规范，设立独立的数据筛选过滤栏、用户列表与设置齿轮抽屉。
  - 默认定时监测频率为 1 小时一次，支持设置基准检查周期与随机抖动（Jitter）。
  - 支持全选或多选后一键批量取关（调用 REST 接口 `/i/api/1.1/friendships/destroy.json`），并在取关后自动同步更新关系标签与本地缓存。
- **定时执行监测日志**：
  - 设立独立的监测执行日志流，详尽记录每次检测的时间点、核验账号名单、未回关天数以及主动取关操作的具体反馈，杜绝黑盒运行。

### 2.2 粉丝管理与互关追踪的一键协同
- **跨模块无缝流转**：
  - 在粉丝管理列表操作列与批量工具栏中，新增「一键加入互关追踪」按钮。
  - 支持用户在日常浏览新粉丝时，将高潜力、高意向的账号直接同步至互关追踪候选池（`mutualNetwork.users`），由互关追踪统一负责后续的主页深度评估、前置看帖、互动与自动化关注调度。
- **消除功能冗余**：彻底打破粉丝管理与互关追踪之间的数据孤岛，避免在粉丝管理中重复开发单账号的复杂看帖与跟帖逻辑。

### 2.3 Codex 统一 UI 样式规范落地
- **操作控件等高统一**：
  - 全局操作按钮（`.btn`、`.icon-btn`、操作列按钮）统一将高度锁定为 30px（`height: 30px; line-height: 28px;`），消除多模块之间按钮参差不齐的视觉违和。
- **单行紧凑排版**：
  - 分页组件、搜索框与分类标签栏统一维持单行排列（`white-space: nowrap`、`flex-wrap: nowrap`），消除不必要的折行与多余垂直空白。
- **全局容器规范间距**：
  - 侧边抽屉与主体工作区容器的内边距统一收敛为标准的 10px，去除多余且不可控的全局 gap 干扰。
- **设置齿轮两端对齐**：
  - 各个业务模块（粉丝管理、互关追踪、评论追踪、回关监测）的设置齿轮按钮一律稳固停靠在首行标题/筛选栏的最右端两端对齐，建立一致的操作直觉。

### 2.4 拟人化行为仿真与随机浮动参数
- **不定频定时浮动**：后台自动化 Alarm 全面实行 `every ± jitter` 动态时间重排，彻底告别机械式整点触发。
- **看帖停留与取关等待抖动**：
  - 在主页阅读推文时，分段下拉模拟（`simulateProfileScrollStep`）引入基准秒数加随机扰动。
  - 连续批量取关时引入随机等待时间，最大限度规避 X 平台的反爬虫与反批量操作风控。

## 三、自带 Grok 智能回评与自动发表闭环（v0.25.2 ~ v0.25.3）

### 3.1 架构解耦与独立模块 `grok-comment.js`
- **模块独立解耦**：
  - 将此前散落且耦合在 `panel.js` 的 Grok 驱动逻辑独立抽离为 `grok-comment.js`。
  - 统一封装：Prompt 模板组装、防伪随机 Nonce 生成、格式定界符提取、推文正文字符清洗以及推特加权字数限制校验（CJK 算 2、ASCII 算 1，严格卡紧在 280 权重内）。
  - 对外暴露标准无状态接口：`generateGrokCommentForTweet` 与 `generateGrokComment`，方便前台互关追踪、后台评论追踪以及手动测试无缝复用。

### 3.2 x.com 与 grok.com 双通道智能探测与自动降级
- **多平台双通道冗余保障**：
  - **优先主通道（x.com）**：优先复用当前登录用户的 `x.com/i/grok` 标签页，直接继承既有推特 Session 与 Cookie 凭据。
  - **备用副通道（grok.com）**：当检测到 x.com 完全不可用时，自动尝试探查并切换至 `grok.com` 备用标签页。
- **避开非致命报错的误报陷阱**：
  - 排障复盘：针对近期 X 平台前端偶发弹出的 `Failed to load models` Toast 或历史会话列表加载失败异常，早期代码容易将其误判为 Grok 完全瘫痪。
  - 优化判据：只要页面核心输入框（`textarea` 或 `[contenteditable]`）已正常渲染且可聚焦，即判定对话功能处于可用状态，正常执行输入与回复生成，防止非致命网络抖动导致回评功能被误杀。
- **双端彻底不可用优雅跳过**：
  - 若系统检测到 x.com 和 grok.com 均未开通或完全不可用，精准记录具体原因并标记“评论不可用”，在自动化流程中优雅跳过回评环节，不阻碍主干关注流程。

### 3.3 推文 DOM 注入与真实发表确认（`page-reader.js`）
- **推文定位与发表流程（`publishReplyToTweetOnPage`）**：
  1. 在帖子详情页，精准锁定与目标 `tweetId` 严格对应的推文 `article` 容器；
  2. 模拟真实用户点击该推文下的 Reply（回复）图标按钮，激活弹窗输入浮层；
  3. 获取回复富文本输入框 `[data-testid="tweetTextarea_0"]`，模拟输入生成的 Grok 回评文本，并触发 input/change 事件以驱动 React 状态同步；
  4. 校验输入内容确实落地且字数未超标后，点击发送按钮 `[data-testid="tweetButton"]`；
  5. 监控并等待回复弹窗自动关闭，以此作为发表成功的刚性判据；
  6. 严格识别并捕获诸如频率限制或重复发送的异常 Toast 提示（如 `Whoops! You already said that`）。

### 3.4 互粉追踪与评论追踪全链路串联与留痕
- **互关追踪前台串联**：
  - 在 `visitScrollAndFollowCandidate` 流程中，当成功关注候选账号后，若该账号近期包含可评论推文，自动调度 Grok 生成针对该推文正文的高质量互动评论，并自动调用发表接口。
- **评论追踪后台串联**：
  - 在 `background.js` 的后台定时任务 `runCommentAutoFollow` 中，针对关注成功的评论者，串联 Grok 回评生成并在来源推文下真实发表。
- **可视化留痕与直观回显**：
  - 界面表格中直接展示真实状态徽标：`✔ 已发表回评: 「...」 查看推文 ↗`，支持用户一键点击直接在新标签页中查验真实评论。
  - 在自动化执行日志详情（`#logsModal`）中完整记录发表状态、评论内容摘要、来源推文链接及失败具体原因，彻底终结黑盒运行。
