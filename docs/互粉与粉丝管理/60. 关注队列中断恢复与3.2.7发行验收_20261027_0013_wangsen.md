# 关注队列中断恢复与3.2.7发行验收

## 问题与现场核验

用户质疑核实后恢复待关注是否会死循环。只读CDP检查发现，截图中的2au3y和Jumane22已在后续调度中记录关注成功，0xCryptoPirates当时正在执行。因此不能把恢复队列等同于必然死循环；历史日志记录当时状态，不代表当前状态。

同时发现ShinPham0908在执行占用到期后重新成为uncertain，保留的结果没有关注attemptedAt。本轮没有额外触发真实关注操作。现场快照在scratch/requeue-live-jobs.json与scratch/requeue-live-audit.json；这些临时文件不纳入发行包。

## 根因与修复

关注队列存储claim会回收过期running任务，原逻辑不区分操作是否发送，全部设为uncertain，导致尚未发送关注的中断任务也要求人工核实。

复用现有存储事务、占用版本隔离与调度器，不新增基础设施。仅queued、claimed、pending、retry等明确操作前阶段，且没有关注、移除关注者、生成或发布动作记录时，恢复为retry。已发送或阶段不明的任务继续保留uncertain，防止重复提交。调度器记录本轮已领取ID，同一轮不重复领取刚失败的任务，下一轮可恢复。人工核实未关注时保存following:false，阻止来源中的旧已关注数据覆盖新核验结果。

没有将核实按钮改为无条件立即关注，没有批量重置历史待核实数据。截图中已经转为uncertain的历史任务也不会仅因安装新版自动改写。

## 验证

- 核心测试1050/1050通过，包括未发送操作的占用恢复、旧执行者写入隔离、已发送关注与移除关注者保持待核实，以及同轮不重复处理。
- 构建检查54/54通过；源码检查132个模块及154个JS/Vue文件调用契约通过。
- 当前浏览器有真实关注任务运行，发行准备不强制重载扩展，以免中断任务。3.2.7构建产物已生成；已加载版本与发行版本应分开核对。
