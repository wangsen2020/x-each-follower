## 问题与证据

首次打开看板的卡顿主要来自本地恢复、重复关系计算与隐藏模块渲染。本次正常启动链路没有发现重新执行全量远程粉丝抓取；X 域 IndexedDB 备份仍需要通过 X 标签页访问，若该页尚未加载，可额外等待页面就绪，不能把这种等待当作远程粉丝增量抓取。

1. 原启动逻辑无条件发起 12 个 durableGet，虽然表面使用 Promise.all，persistent-db.js 内部仍串行执行。local 已有的大对象再次跨标签传输。
2. ownFollowingHandles、ownFollowerHandles 在每个互关及评论账号的计算中反复构建；monitorUserStatus 又对队列调用 find，造成嵌套扫描和大量短命集合。真实 CPU 采样的主要热点集中于这些函数。
3. 日志初始化在 currentLogsScope 声明之前调用 renderLogsModal，真实浏览器捕获到“评论追踪记录加载失败：Cannot access 'currentLogsScope' before initialization”。异常中断评论数据的 local 读取，后续又从备份恢复并回写整份对象。
4. 未打开的列表、日志预先执行渲染；renderQueue 本身调用 renderMonitorList，启动还会重复调用后者。

## 实现

- 新增 panel-data.js：每轮计算创建一个队列状态 Map 与关注、粉丝 Set，批量筛选和渲染共用该索引。后续轮次重建，避免原地修改用户数据时命中旧缓存；保留重复 handle 的首条队列记录优先语义。
- 记录 local 读取时的键存在性，仅对缺失键读取 durable 备份；存在的空数组和空对象保留。应用备份前再次检查 local，避免用迟到的恢复结果覆盖新记录。
- autoFollowLogs、monitorLogs、unreciprocatedLogs 改为打开日志时加载。写日志前也先加载已有日志；读取失败直接中止该次写入并允许重试，不用空缓冲区覆盖历史。读取备份期间出现的 local 日志优先。
- 隐藏日志不构造 DOM；隐藏模块保留数据与侧栏计数，切换进入时渲染。删除重复首屏渲染；没有恢复记录时不做第二次全集合乱码清理。
- 将日志作用域声明提前，消除初始化异常。保留现有业务状态和自动化配置。

## 下一阶段技术方案：模块懒加载与记录级分页

补充时间：2026-10-19 17:00；作者：wangsen。**状态：用户已批准。** 当前开发分支是 `feature/next-iteration`。本节是下一轮设计，不是上述启动优化的已完成成果。由 Grok 4.7 开发，Codex 负责代码审查、迁移完整性检查及 CDP 实机验收。阶段 A 的入口清单与适配契约已写入本文；阶段 B 只新增未接入的 `record-repository.js`。不执行迁移、不清理现有数据、不把真实读写切到新库。

### 1. 当前瓶颈与改造边界

当前 panel.js 启动仍读取 monitor、profileCache、mutualNetwork、commentTracking、unreciprocatedTracker 等整模块对象；列表分页主要发生在内存数组上。隐藏模块不渲染，不等于隐藏模块不加载。persistent-db.js 在 X 域 IndexedDB 中也是按模块保存大对象，恢复时仍需整对象传输。

follow-queue-store.js 已使用扩展域 IndexedDB，现有 accountId 和 accountTarget 索引，但 jobs.getAll 与 outcomes.getAll 入口仍需逐一追踪调用者。不能仅改看板，而让后台调度、统计、筛选或自动入队继续反复扫描全表。

本轮覆盖粉丝管理、互关追踪、评论追踪、回关监测、执行日志及关注队列数据查询；保留现有关系判定、筛选、搜索、标签、来源溯源、队列防重与自动化设置语义。Grok 会话复用和验证识别逻辑不属于本次数据结构重写范围。

### 2. 存储选择：优先 IndexedDB，暂不引入 SQLite

| 方案 | 适用性 | 本轮决策 |
| --- | --- | --- |
| 扩展域 IndexedDB，按记录存储和建索引 | 与现有队列技术一致，适合账号隔离、列表分页、事务增量更新 | 推荐作为业务主库 |
| SQLite WASM 加 OPFS | 可以提供 SQL；需要另行验证 Worker 生命周期、文件锁、多窗口并发、打包与备份恢复 | 保留为后续候选，不直接替换 |
| 原生 SQLite 加本地宿主程序 | 适合已有桌面客户端的架构，但需要安装和维护额外本地程序 | 当前纯扩展产品不采用 |

当前问题主要是整对象读写、重复计算及全量传输，尚无证据表明 IndexedDB 本身吞吐不足。把整对象搬入 SQLite 或执行 SELECT 全表再在 JS 分页，仍不能解决问题。先修正查询形态，再用相同数据集比较引擎，避免把迁移风险和运行架构复杂度同时引入。

Chrome 官方说明扩展页面与 Service Worker 可使用 IndexedDB，扩展域存储也有自身生命周期；不能把主库误当作卸载后仍可恢复的备份。[Chrome 存储说明](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies)

SQLite 官方提供多种 OPFS 持久化方案，Worker、锁竞争和并发限制需要按所选 VFS 验证；不能笼统认定所有方案都需要相同隔离配置，例如 opfs-sahpool 可用于不能设置 COOP/COEP 的环境。对本项目而言，这些是额外的兼容性验证任务，并非已经验证可直接接入。[SQLite 持久化方案](https://www.sqlite.org/wasm/doc/trunk/persistence.md)

原生路线需要 Native Messaging 宿主及相应安装配置，改变当前无需附加程序的使用方式。[Chrome Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)

后续只有在复杂多表关联、全文检索需求明显增长，且正确索引后的 IndexedDB 仍未达到验收指标时，再做 SQLite WASM 的独立对照实验。数据条数本身不是更换引擎的充分理由。

### 3. 目标数据分层

chrome.storage.local 仅保留少量偏好、账号绑定提示和轻量状态；业务记录进入扩展域 IndexedDB。主库元数据中的 schemaVersion、activeGeneration 与 revision 是权威状态，storage 中的镜像标志不得决定迁移是否成功。

现有关注队列数据库先保留，通过版本升级增加查询索引，避免无必要地搬动已执行结果与租约。其余模块共用新业务库与统一 Repository 接口。不同数据库之间不假设存在原子事务；跨库入队使用可重试操作 ID 与持久化 outbox，保留 accountTarget 防重。

| 记录类别 | 键与索引方向 | 读取规则 |
| --- | --- | --- |
| 账号、迁移元数据 | accountId、schemaVersion、generation、revision | 启动只读当前账号及轻量摘要 |
| 用户档案 | accountId 与 userKey；标准化 handle 别名索引 | 按当前页的用户键批量读取 |
| 模块成员列表 | accountId、module、userKey；组合索引包含状态、排序值、userKey | 按索引范围与游标查询 |
| 关系状态与列表投影 | accountId、userKey；记录各来源、时间与已知或未知状态 | 页面直接读取投影，不依赖其他模块已加载 |
| 标签关联 | accountId、module、tag、排序值、userKey | 单独关联记录；不依赖不支持的复合 multiEntry 索引组合 |
| 帖子、评论和详情 | 账号、帖子 ID、用户键及来源引用 | 打开详情时加载，列表不携带完整正文集合 |
| 执行日志 | accountId、scope、时间、唯一事件 ID | 按时间倒序分页，详情单独读取 |
| 摘要、变更日志、待备份记录 | accountId、module、revision、operationId | 随业务变更事务更新或记录待处理状态 |
| 现有队列 | 账号加状态、到期时间、稳定任务 ID 索引 | 调度只查到期候选，页面只查当前页 |

User Rest ID、Tweet ID 全程使用字符串。账号归属与目标用户身份分开：有可靠用户 ID 时优先使用 ID；只有 handle 时保留临时身份和别名映射，补全 ID 后按规则合并并保留来源。旧数据无法确定所属账号时放入待确认分区，不能直接归到当前登录账号。

迁移保留未识别字段的原始载荷，避免新模型遗漏历史字段。队列 outcomes 的防重历史独立于日志展示保留策略，清日志不能删除防重结果，也不能重置已完成任务、租约或自动化配置。

### 4. 模块懒加载与跨模块一致性

1. 首次打开只加载页面骨架、账号、设置、侧栏摘要与当前模块第一页。隐藏模块不读取记录、不开详情、不读取日志；缺失备份的恢复不阻塞正常已有数据的首屏。
2. 每个模块维护 unloaded、loading、ready、error 状态；相同查询合并请求，失败可重试。加载中不能被当成空数据，更不能回写空集合。
3. 切换账号、筛选条件或模块时更新请求代号，丢弃迟到结果。页面只缓存有限页，例如最近三页；缓存不是主数据源。
4. 后台发送账号、模块、受影响 ID 和 revision 等轻量失效通知，页面只刷新受影响查询。重新打开或通知中断后通过 revision 检查补齐，不依赖通知必达。
5. 粉丝、互关、评论共享的关系判定改由记录库提供。当前 getNotMutualUsers、syncAllActiveFollowedUsers 等跨模块逻辑不能读取未加载的空数组后得出错误结论；后台任务不依赖看板打开。
6. 可计算的计数与成员变更在同库事务内更新，初始化修复采用后台分批任务。侧栏计数不通过加载全表获得；暂未算好的计数明确显示更新中。

### 5. 真分页、筛选与搜索

统一接口建议为 queryPage，输入账号、模块、筛选、排序、cursor、limit；返回当前页、下一游标、revision 与可用计数。默认保留现有每页 20 或 50 条选择，单次最多 100 条。稳定排序必须包含唯一键，避免相同时间记录翻页重复或遗漏。

普通列表按组合索引范围读取 limit 加一条；仅按本页 ID 获取关联投影。禁止无界 getAll 后 slice，禁止深分页从第一页逐条跳过。游标绑定账号、筛选哈希、排序和数据代次；数据变更导致游标不再有效时重新查询并提示刷新，不伪装为稳定快照。

优先提供上一页、下一页和准确的已知总数。现有任意页跳转需要额外的分页锚点：本方案建议保留已访问页快速跳转，未建立锚点的远页不通过全表读取实现；如必须保留任意数字页直达，应单独增加可失效的稀疏锚点后台任务。该交互调整属于本方案待确认范围。

搜索不能悄悄缩减功能：handle 或名称前缀可用标准化索引；简介、评论正文的包含搜索需要独立搜索设计。第一阶段保留原语义，使用可取消、分批游标扫描和进度反馈，不把全集合传到看板，也不阻塞主线程；随后按实测热点决定是否增加词项或 n-gram 索引。中文、短词、多标签组合和混合排序分别测试。复杂条件允许后台分批扫描，但不得宣称所有查询均只访问一页记录。

精确筛选总数采用可用索引计数或缓存摘要，复杂搜索计数异步完成；输入搜索词时防抖和取消旧查询，不能每次按键同步遍历全库。批量操作区分“本页选择”和“所有匹配项”，后者以查询条件加版本创建后台分批任务，不向前端一次返回全部 ID。

### 6. 增量写入与后台任务

所有写入者必须收口到 Repository：包括采集、关系同步、Grok 结果、手动操作、自动调度、日志、设置导入和备份恢复。禁止新旧实现同时各自覆盖整模块快照。

记录更新、关系投影、相关计数、revision 和备份 outbox 在同库事务提交；事务外进行网络请求。批量写入以 100 至 500 条为初始调优范围，根据记录体积与耗时缩小；不能在单个长事务中导入全库。

每次操作具有稳定 operationId，重试幂等；后台任务把检查点、租约和失败状态持久化，不能仅靠内存队列防重。Service Worker 重启后继续处理，用户界面可显示阶段与失败原因。业务“已保存”以主库事务完成为准，“已备份”另行确认。

### 7. 迁移与数据完整性保护

迁移的必要全量读取与日常访问分开：chrome.storage.local 的旧大对象无法按其中第几条读取。首次转换必须按旧键逐个读取，一次只保留必要模块，分批写入新库；这一步不冒充记录级读取优化。旧 X 域备份也按其实际格式处理。迁移不放在首屏同步阻塞路径中。

迁移流程如下：

1. 盘点旧键、记录数量、账号归属、字段、日志、队列结果及设置；生成原始快照校验值。评估主库、保留快照、索引及迁移临时空间，空间不足明确中止，不能删旧数据腾位置。
2. 先让所有写入入口识别持久化迁移状态。迁移期间暂停相关账号的自动化写操作并等待在途任务结束，界面可继续只读访问旧数据；新写请求明确拒绝并提示稍后重试，不把未保存操作报告成成功。没有完成全部写入入口审计，不允许开始迁移。
3. 保留旧存储原样，并准备可导出的原始备份；在新库暂存代次中按模块、批次写入，记录最后已完成检查点。转换按稳定源键幂等，重复执行不会生成重复记录。
4. 校验不只比较总数：对比唯一身份、账号分区、状态、来源、帖子及评论引用、关系、设置、日志顺序和字段内容。使用规范化字段摘要逐批核对；拆分与去重的数量变化必须有映射明细，冲突记录保留并报告。
5. 校验通过后，在新库单个事务中切换 activeGeneration，更新迁移状态；旧 storage 状态只作为镜像。恢复所有写入走新 Repository，后台任务按原状态继续，不重新执行已完成动作。
6. 中断或校验失败时保持旧库可读，暂存数据不视为正式数据。重启后首先恢复迁移状态，未确认写入目标前保持相关自动化暂停；不能因内存锁消失重新启动旧写入者。
7. 切换之后回滚不能简单恢复旧快照，否则会丢掉新记录。保留增量变更日志，回滚工具需把切换后的新增、修改和删除重放到兼容格式并重新校验。直接安装不认识新结构的旧版本不算受支持回滚路径，须先导出或执行回滚工具。

短时只读窗口是本方案为迁移一致性选择的取舍；开始前显示影响范围和进度，后台分批让出执行时间。大数据集耗时必须实测，不能提前承诺固定秒数。只有演练和完整性校验通过后才允许迁移用户实际数据。旧数据和旧备份本轮不自动删除，后续清理需要独立确认。

### 8. 备份、恢复与删除语义

保留 X 域恢复能力，改为版本化清单加分块记录或增量批次。新主库写入时同步记录 outbox，异步备份；完成所有分块并验证校验值后才更新“最后完整备份”指针。中断时使用上一份完整备份，不读取半份新快照。

删除也要写 tombstone 与版本，避免旧备份恢复已删除用户。恢复必须比较版本、账号与删除记录，不能用“哪个对象条数更多”判断优先级。备份不可访问时保留待同步状态并允许重试，不在每次打开看板时创建 X 页面阻塞首屏。

扩展主库与 X 域备份无法跨域原子提交，必须分别展示本地保存和备份完成状态。卸载前尚未完成备份的新数据仍有风险，应提供导出和待同步提示。X 域备份依赖对应浏览器 profile 与站点数据仍在，不能承诺清空站点数据或磁盘损坏后仍可恢复。数据安全验收以原始副本保留、完整性核验、故障恢复和增量回滚演练为依据。

### 10. 验收标准与证据

先在隔离数据库使用 1 千、1 万、10 万条合成或脱敏记录测试，包含多账号、重复 handle、身份补全、长简介、大量评论、同时间排序、空集合和历史未知字段。记录冷启动与热启动各轮数据，不把单次最优值作为结论。

拟定性能目标，以下均未实测：普通索引列表每页最多 100 条，相关记录读取数量随页大小增长；热查询 P95 争取不超过 300 ms，冷启动当前页争取 1 秒内可用，以固定测试设备和数据集记录实际结果。未达目标需要分析，不能把目标写成已达到。复杂全文搜索单独报告扫描量、可取消性和进度，不套用普通索引查询指标。

必须记录数据库调用次数、实际返回记录数、跨进程消息字节量、首屏时间、长任务及内存趋势。首屏不得读取隐藏模块、全部日志或全部队列历史；正常翻页不得无界 getAll；导出、迁移、审计允许遍历，但必须分批且不阻塞交互。

正确性检查包含：迁移中断与续跑、磁盘配额不足、事务失败、备份不可用、多看板并发、账号切换迟到响应、删除后恢复、主库升级被旧连接阻塞、后台重启，以及切换后产生新数据再回滚。不能只比较 UI 上的数量，应逐记录核验内容与来源，确认队列 outcomes、租约和设置未被重置。

运行 npm test、静态检查及新增迁移/分页/并发测试。CDP 使用 tools/cdp-session.ps1 附加现有已登录 profile，以测试专用后台标签验证模块切换、筛选、搜索、分页、详情、日志、刷新和重启；先对真实数据做只读盘点和备份，不用关注或发帖动作制造性能负载。完成后只关闭本次测试标签。最终报告分开列出测试副本结果、真实数据结果和未覆盖项，附迁移前后校验报告。

### 11. 待确认决策

已批准的组合是：扩展域 IndexedDB 记录主库、现有队列库渐进升级、隐藏模块不加载、索引游标分页、短时只读迁移、保留旧副本与 X 域备份、本轮不引入 SQLite。页面跳转按第 5 节采用已访问页与上一页/下一页方案；复杂搜索保留语义并异步分批执行。批准分支为 `feature/next-iteration`。真实数据迁移仍须等阶段 B 的演练和阶段 C 的全部入口适配完成。

### 13. 迁移适配契约与阶段 B 起步

阶段 B 的记录库是 `record-repository.js`，迁移演练是 `record-migration.js`。两者都没有注册到 manifest，不读取 `chrome.storage` 或 X 域备份，也不改动真实数据。数据库名 `x-each-follower-records`，版本 1。对象库为 `meta`、`records`、`tombstones`、`summaries`、`outbox`、`migrations`。

记录主键和索引都带 generation，不用“只改 activeGeneration 指针、记录仍落在同一键空间”的做法。`storageKey` 与摘要键是数组元组 `[accountId, module, generation, userKey]`，不是用 NUL 把几段拼成一个字符串，因此标识本身含有 NUL 也不会和别的账号或模块撞键。`scopeSort` 为 `accountId, module, generation, sortKey, userKey`，`scopeStatusSort` 再插入 `status`，`accountGeneration` 用于按代次扫描。`queryPage` 的范围包含正在读取的那一代；未激活的暂存代不会出现在默认查询里。`limit` 为 1 到 100 的整数，多读一条判断下一页。游标绑定账号、模块、筛选哈希、排序、generation 与 revision。`last` 必须是长度正好的元组：无状态筛选为 5 段，有状态筛选为 6 段；账号、模块、generation 必须与本次查询一致，其余段必须是字符串。伪造另一账号的 `last`、改长度或改类型都抛 `RecordCursorInvalidError`。写入使该账号 revision 增加后，旧游标同样失效。

业务载荷放在 `payload` 信封里原样保留。`userKey` 只做索引；调用方同时给出 `userKey` 和 `id` 时，`id` 保持原值，包括超出安全整数、无法精确表示的数字，以及必须全程使用的字符串 ID。部分更新合并进已有 `payload`，不丢弃未知字段。删除把这份 `payload` 留在墓碑上。

`putRecords`、`deleteRecords` 与 `putTombstones` 在同一事务里更新记录或墓碑、摘要和 outbox。`operationId` 只有在账号、模块、类型和规范化内容都一致时才返回第一次的结果；换模块、把写入重放成删除、或换了记录内容，都直接拒绝，不会悄悄交回上一次的结果。暂存代写入不推进当前代的 revision，因此不把未激活的数据暴露成当前页。

打开数据库失败后会丢掉这次 Promise 并允许重试。连接收到 `versionchange` 时关闭自己，避免挡住升级。`blocked` 只等待有限时间（默认 3 秒，测试可注入），超时后失败而不是一直挂起。`close()` 关闭当前连接，之后的调用会重新打开。

`record-migration.js` 把旧快照无损拆开再装回。它会遍历 `monitor.users`、`monitor.followingUsers`、`monitor.queue`、`commentTracking` 与 `comments` 的 `users`/`posts`、三份日志、`profileCache`、互关、回关、分析行、原始行，以及未知的嵌套数组和全是对象的映射。身份用源路径，不用 handle 或业务 id 去重；同一 id 出现多次会保留多条。只有记录自己带有非空字符串 `accountId` 才归入该账号，否则模块和账号分区都是 `unassigned`，不会把快照上的当前账号套到子记录上。源对象不被修改。

嵌套数组和对象映射拆成子记录。父记录的 `payload` 只保留叶子字段，骨架上的字段顺序指向子记录，不再把子对象原样留在父载荷里。回滚导出按这个引用把子记录盖回去，所以改、删、增子记录都会出现在导出结果里，不会留下一份过期副本。新增记录必须带 `sourcePath`。粉丝可以回到 `monitor.followingUsers` 或 `monitor.queue`，不会一律追加到 `monitor.users`。缺少路径，或两条记录落到同一路径，导出直接拒绝。身份是账号、模块和 `userKey` 一起，不用单独的 `userKey` 把不同分区并成一条。

不可变清单放在 `migrationManifests`：骨架、代次、导入开始时的 `activeGeneration` 与 `revision`、每条记录的 SHA-256。哈希用浏览器 `crypto.subtle` 的 SHA-256，迁移模块不引用 Node。`migrations` 里的检查点只有状态、`nextIndex` 和封存时的代次修订号，每批只重写这份小记录。校验开始前先记下每个暂存代的修订号，再读记录。记录数和键必须与清单一致，多出来的记录算失败。封存发生在同一个事务里，而且只有修订号仍等于读取前记下的值才封存。已经是 `verified` 或 `active` 时再次校验直接返回原检查点，不把激活后的正式写入当成校验失败。旧代上相同 `userKey` 的正式记录不算暂存泄漏。校验通过后该代标成 sealed。之后再往这个代写入会失败，直到它被激活并解除封印。`activateMigration` 在同一个事务里核对：状态仍是 `verified`、封存修订号没变、每个账号的当前代和 revision 仍等于导入开始时的基线。正式数据在导入之后有新写入，或另一条迁移先切换了代次，激活都会拒绝，不能覆盖更新的正式数据。

导入写入单独分配的 generation，按 1 到 500 条分批提交。失败留在原代，同一 `migrationId` 按检查点续跑。激活之后的 `exportRollback` 按旧结构导出，并单独列出切换后的新增、修改和删除；原先已删除的墓碑仍在导出结果里。

Codex 用 Chromium 对一份复制出来的真实快照做了演练：12177 条记录往返后内容不变，耗时 51536 ms。同一次验收仍拒绝了阶段 B，原因是嵌套回滚、校验后还能改暂存代、键拼接、导出身份和整份检查点重写。上述修正针对这次拒绝，还没有经过 Codex 复验。这次演练没有把正式读写切过去，也没有改队列库。

## 15. 写入队列的更简单要求

上面第 13 节里的跨页面锁、写入租约、`AsyncLocalStorage` 守卫和严格迁移协调器已经作废。用户明确不要求业务事务、极端一致或失败后整库回滚。坏记录可以跳过并报告。一次写入失败就让这次请求失败，后面的请求继续。

当前做法：

- 后台服务工作者持有一条 Promise 队列（`storage-write-queue.js`）。每个 `enqueue` 把自己的结果返回给调用方。失败只拒绝这一次，并用 `onError` 记下原因，不把队列卡死。
- 扩展页面不把函数传到后台。`storageWrite` 消息只带 `localSet`、`localRemove` 或 `syncSet` 和可序列化的数据。后台适配器按这个顺序写 `chrome.storage`。
- 读和分页不进这条写队列。IndexedDB 只在记录库或队列库自己的 `put` / `delete` 事务里使用，本批不另加锁。
- 真实迁移仍然关闭。`record-repository.js` 和 `record-migration.js` 继续只做演练，不读取、不删除现有本地数据或 X 域备份。目的库失败时不得删掉整份旧快照。
- 看板懒加载分页还没接上之前，不启动正式迁移。

还在直接写存储、没有改走 `storageWrite` 的路径：执行日志 `appendExecutionLog`、自动关注尝试 `recordAutoFollowAttempt`、X 域 `durableSet`、关注队列库、Grok 验证通知、`networkTemplates`、验证会话，以及 `automation-recovery.js`、`verification-self-message.js` 里的设置写入。这些不是已经收口。


Codex 独立验收：285 项测试和静态检查通过。重载真实扩展后，经 CDP 从测试页调用后台 `storageWrite`，连续提交正常写入、无效写入、正常写入。无效命令以及真实 `chrome.storage.local.set` 参数错误均只影响当前请求，后续写入成功，最终读取为最后一次值；测试专用键已删除。原 11 个业务键再次与备份校验一致。此结果只验收简化写入入口，不代表所有写入路径、主看板懒加载或记录级分页已完成。
