# 客户端版本升级与数据迁移统一方案

<a id="client-data-upgrade-design"></a>

创建时间：2026-10-24 22:04，Asia/Shanghai。作者：wangsen。状态：首期归档记录库实现与验收已完成，含隔离完整扩展及后台重启验证，当前结论见第 14 节；未切换正式用户数据、未推送或发行。

本稿经整体审查收敛，替代此前追加形成的通用迁移框架设计。首期目标是让一个现有数据库可靠接入 Dexie，验证跨版本升级和失败恢复，明确写事务范围；不把所有存储、备份与并发机制同时重构。后续推广仍属于本需求，按实际落地情况更新本文。

## 1. 审查结论与范围收敛

| 原方案问题 | 本稿处理 |
| --- | --- |
| 已选择 Dexie，又设计通用 runner、注册表、依赖图、定义哈希与全局序号 | 常规数据库升级全部交给 Dexie；删除自研通用迁移引擎要求 |
| 新增独立控制库及 datasets/steps/leases/reports 四表，没有首期具体任务支撑 | 首期不建控制库，不新增全局 datasetId/epoch/fence 协议 |
| 要求每次迁移分批续跑，与 Dexie upgrade 的事务语义混淆 | 明确两类恢复：普通升级失败整笔回滚并重试；只有已有或实际需要的长任务使用检查点 |
| 以全局序号标记数据已升级，可能掩盖不同数据库、恢复导入的真实状态 | 各库已提交版本是依据；应用版本仅用于展示和诊断 |
| 要求全客户端启动等待跨域恢复，扩大故障影响范围 | 只阻塞依赖未就绪数据的操作，沿用现有恢复边界，不无故增加启动全量扫描 |
| 并发方案扩展到页面租约、跨库提交及备份系统重构 | 首期仅审计并收窄事务范围，不删除现有业务队列；性能优化另设触发条件 |
| 禁止修改任何已发布迁移，但后续修复永远无法越过失败的旧脚本 | 已成功应用的变化用新版本修正；阻塞升级的旧回调允许有明确记录的最小兼容修复，必须覆盖所有受影响基线测试 |

长期原则：先采用成熟开源库，以更快、更可靠交付产品为目标。只实现库不能表达的业务规则，不为假设的未来需求建设通用平台。

## 2. 选型与首期交付

选定 [Dexie.js](https://github.com/dexie/Dexie.js) 开源核心库，负责 CRUD、索引、事务和 version().stores().upgrade() 版本迁移。无需 Dexie Cloud，不同时引入 idb 或 RxDB。实施时锁定经验证的稳定版本并随扩展本地打包。

### 2.1 首期必须完成

1. 以 `src/features/records/record-repository.js` 为首个接入边界，保留对外方法及现有库名、记录、主键、索引和模块迁移语义。实施前确认它的真实调用路径；如当前活跃记录主库另有入口，先修正试点选择，不为替换一个非活跃库制造无效改造。
2. 在内部采用 Dexie，并验证既有原生 IndexedDB 数据库的版本映射。首期不要求同时改造 projection、日志、队列或 X 域桥接。
3. 使用各库目标版本及成功打开/必要验证结果判断就绪，在涉及试点库的启动、消息与写入入口等待就绪。保留现有模块恢复逻辑，不另造全局协调器。
4. 按 repository 方法列出最小事务范围，去掉无理由的“所有写入一律声明全部表”；确实需要多表原子性的操作保留完整范围。
5. 用历史副本与测试迁移夹具完成跳版本、失败重试、旧连接阻塞、账号隔离及数据完整性验收。

首期不为展示框架故意增加业务字段、过滤用户数据或搬表。生产包只包含真实需求所需的结构变化；用于证明多级升级的转换保留在测试夹具中。若采用 Dexie 本身需要数据库版本变化，该接管升级就是首个真实交付。

### 2.2 首期不做

不新建升级控制库、通用迁移目录体系、依赖 DAG、全局步骤序号、跨库两阶段提交、通用租约/栅栏服务、隔离区管理平台或自动回滚平台；不拆库、不统一所有历史备份格式、不增加页面并发租约、不批量删除 Promise 队列。不因本方案改动 X 操作的并发、额度或启停状态。

这些并非永久禁止：出现具体跨库搬迁、无法在一次事务内完成的数据转换或实测性能瓶颈时，再定义该任务的最小协议和验收，不预先实现。

| 位置 | 现状 | 本轮处理 |
| --- | --- | --- |

## 4. 版本与跨版本升级

只保留两种必需版本：应用版本 appVersion，以及每个数据库的 Dexie schema 版本。已有 record migrationId 继续服务它原有的导入/恢复任务，不新增第三套全局迁移序号。

应用发行说明可记录“该版本要求各库达到哪个版本”，运行时以各模块的数据库定义为准，不维护重复的版本清单。纯 UI 发布可不变更数据库版本；同库数据修复即使不改变索引，也可新增 Dexie 版本及 upgrade 回调。

### 4.1 跳版本示例

下面是说明机制的假设，不是项目真实发行历史：

| 应用版本 | 该库目标版本 | 变更 |
| --- | --- | --- |
| 1.1.0 | v1 | 旧结构 |
| 1.2.0 | v2 | 补字段 |
| 1.3.0 | v3 | 调整表内数据 |
| 1.3.1 | v4 | 修复明确错误 |

已有 v1 数据打开目标 v4，Dexie 按保留的版本定义执行所需升级。中间版本回调必须随支持范围保留，不能只判断“上个应用版本是否恰好等于 1.3.0”。全新安装直接建立最新结构，创建记录时仍需写入完整默认值。

**恢复语义必须准确**：一次从 v1 打开 v4 的升级处于 IndexedDB 的升级事务中；若其中回调失败并导致事务 abort，本次升级修改整体回滚，数据库仍是 v1，重试会再次执行所需回调。不能把 v2 回调运行完当作独立持久完成，也不能写“从 v3 检查点继续”。另一次启动之前就已成功提交到 v2 的数据库，才从 v2 继续。

升级回调不发送网络请求或执行外部动作，不吞掉应使事务失败的错误；使用固定转换规则，避免依赖未来会变化的默认值函数。大规模转换不能强塞进一个长 upgrade 事务，按第 7 节处理。

### 4.2 成功标记

- 数据库成功提交后的版本是常规升级凭据，不能在 onInstalled 触发时提前写成功。
- 若需要显示 `lastReadyAppVersion`，只在本次声明参与检查的模块全部成功后更新；它是诊断摘要，不能据此跳过打开数据库、既有恢复或导入校验。
- 未纳入接入范围的模块不得标称“全客户端已完成统一迁移”。摘要保存失败可重新计算，不重复执行外部动作，也不把已提交的数据回退。
- 首期不为了这个摘要新增表或库；优先沿用现有本地诊断/设置存储，不同步到其他设备。

## 5. 存量数据库接入与就绪检查

### 5.1 原生库接管

Dexie 的声明版本与原生 IndexedDB 版本存在乘以 10 的映射。实施前先在副本中读取真实库版本、结构及所有调用者，再固定接管策略；不能把原生版本 1 直接当 Dexie 版本 1 而不检查实际升级影响。无 schema 声明的动态打开可以用于调查，但最终升级必须有明确且经验证的版本定义。

试点库所有打开入口必须适配同一版本策略，包含仍可能存活的旧页面。旧代码若继续按较低原生版本打开，会失败；不能以“新页面测试通过”代替跨页面兼容验收。无法排除旧写入者时阻塞相关操作并提示重载，而不是并行迁移。

### 5.2 最小就绪实现

每个受影响模块复用一个初始化 Promise：打开库、等待 Dexie 升级成功、执行原有必要恢复/后置检查后才返回。失败清除失败 Promise，以便显式重试；每次后台重启重新检查，不依赖内存保留。

初始化 Promise 只是当前实例的去重。普通 schema 升级的跨连接互斥交给 IndexedDB；首期不新增数据库租约。已有跨存储恢复的互斥仍沿用原机制，不宣称它自动获得新的全局保证。

就绪检查覆盖依赖试点库的后台消息、alarm、顶层 schedule、面板保存、storage.onChanged 后续写入及恢复入口。诊断状态读取不应等待同一个失败任务；无关模块不因试点库错误被无条件停用。新格式数据在就绪前不得被业务读取；不新增临时旧格式只读适配层。

## 6. 最小事务范围与并发决策

IndexedDB 普通事务按 object store 集合调度：只读可以共享作用域；涉及写入且表范围重叠时需等待；不同 key/账号仍可能在同一表竞争。不同表允许独立调度，但不保证浏览器物理 IO 并行。结构升级是单独的 versionchange 事务。

保留现有库划分。按方法声明表集合，不能用默认全表范围掩盖依赖，也不能只列写表而遗漏事务内读取的 meta、revision、activeGeneration。共享 meta/outbox 仍可能是热点，先接受必要的一致性开销，有证据后再优化。

| 操作 | 事务原则 |
| --- | --- |
| 读取记录及当前活动代 | 实际需要的 meta+records，readonly |
| 更新单独迁移状态 | 仅在确实无其他依赖时使用 migrations |
| 正式记录写入 | 按方法纳入 records、meta、summaries、tombstones、outbox 中必需项；记录和相应备份任务保持原子提交 |
| 迁移激活、删除等跨表操作 | 包含所有一致性依赖；宽事务可以合理存在 |
| 日志追加与分页 | 现有 logs/scopeRows/backupOutbox 原子关系保留；分页只读不进入新的全局写 limiter |

同库读改写在同一事务内完成。计算在事务外时，提交前校验源 revision；网络、导航、Grok、计时器和用户交互不放进事务。只在事务完成后报告成功，不把请求 success 当提交。无需为这些完整短事务新增 p-limit(1)，也不新写一个通用调度器。

### 6.1 队列处置清单

本次搜索未发现 p-limit/pLimit 依赖或调用，实际串行主要来自 Promise chain。以下区分“本期动作”和“未来删除条件”，不是要求本期全部完成。

| 机制 | 首期 | 以后可移除/收窄的条件 |
| --- | --- | --- |
| record-repository.js 全表 write | 按操作收窄事务作用域；不是删除业务队列 | 通过调用路径、原子性与范围测试 |
| execution-log-store.js enqueue/chain | 保留 | 完成恢复门禁，验证日志正文、索引、episode 合并、时间字段及清理语义均由事务/明确协议保证后，可移除 append 外层串行 |
| append 内 await flushOutbox | 保留接口行为，列为后续优化候选 | 实测备份拖慢本地提交后，将可靠 outbox 发送与本地提交解耦，并明确 API 的“本地成功/备份成功”区别 |
| execution-log.js writeQueue | 保留 | 旧 chrome.storage 数组读改写的所有调用均淘汰后，删除整个旧路径 |
| persistent-db.js dbOperationQueue | 保留 | 实测桥接队列成为瓶颈，再单独解决共享页面在途使用、失效和关闭；不得直接移除导致页面提前关闭 |
| record-runtime.js mutationChain | 保留 | 跨库记录/投影、关系重算、revision、备份一致性有等价保证后再按业务范围收窄 |
| writes.enqueue/storage-write-queue.js | 保留 | 逐调用确认旧数据 absorb、恢复及增量序号读改写已由事务或现有可靠协议覆盖 |
| persistIncremental 非原子 fallback | 保留现有约束 | 废除 fallback 或将 head/seq/operationId 改为同目标库原子追加；内存队列不构成跨上下文完整保证 |
| knowledge-budget concurrencyLimit=1 与对外动作限流 | 保留，不属于本期数据库优化 | 需要独立的外部服务/会话/额度证据，不能因数据库并发而调整 |

结论：首期不删除已有业务队列，也不新增全局队列；减少的是过宽数据库事务。日志外层队列是后续明确的可移除候选，其他队列必须先解决各自的一致性或资源生命周期问题。同表写入仍会由数据库排队，不能承诺删队列即提升写吞吐。

## 7. 长任务、搬表与业务修复的最小边界

首期不新增具体长任务。已有 record-migration 的暂存、校验、检查点及激活继续复用。以后遇到真实需求时按下表选择，不要求所有变更都走同一套框架。

| 真实需求 | 最小方案 |
| --- | --- |
| 小规模字段修复、同库搬表 | Dexie upgrade 事务；转换后检查规则，不做额外全局步骤账本 |
| 大数据量、一次升级事务耗时不可接受 | 用该模块现有迁移能力分批处理；数据与批次检查点尽可能同目标库事务，稳定主键/operationId 支持重放 |
| chrome.storage/X 域到扩展库搬迁 | 保留源副本，复用模块暂存与校验，再切换；只有具体搬迁需要时才设计跨存储提交凭据 |
| 无效数据过滤、去重 | 固定规则，保留恢复材料或带原因的隔离副本；验证数量与引用，不靠相似文本武断合并 |
| 可重建数据 | 先核实它确为派生数据，再从权威来源重建，不能仅根据文件名推断 |

仅有一个具体业务迁移时，使用明确函数与现有检查点即可，不先建设注册表、依赖解析、插件适配器和通用租约系统。若确需多执行者协调，先限制写入所有权并评估平台/现有机制；不能为了“薄协调层”再手写分布式锁框架。

校验内容随变更选择：主键、账号归属、引用和预期字段变化。未改变内容可比较哈希；有意转换不能要求前后原文哈希相同。队列 outcomes、已发私信记录、删除标记及 uncertain 结果必须保留；迁移不能产生 X 对外动作。

## 8. 旧数据、恢复与失败处理

| 场景 | 最小处理 |
| --- | --- |
| 旧用户没有应用升级标记 | 依据实际数据库版本、结构及已有模块迁移凭据判断；不直接写当前版本宣告完成 |
| 首次安装 | 当前库为空不代表所有外部备份为空；保留原有恢复检查，不新增全客户端全量探测。对依赖恢复的模块，读取失败不能当作空数据 |
| 已完成 legacy 迁移 | 继续使用原有激活/指纹凭据，禁止重新导入陈旧快照 |
| 旧备份导入 | 数据库已是最新版不会自动触发旧备份内容的 upgrade；导入入口必须识别备份格式并复用已有转换。暂不支持的格式拒绝导入，不把未升级内容直接写入新库 |
| Dexie 升级事务失败/配额不足 | 事务回滚，保留原数据并报告原因；重试升级，不清库、不假报完成 |
| 已有分批迁移中断 | 按其现有检查点续跑，不再登记第二套全局进度 |
| 旧连接阻塞 | 关闭本方旧连接，提示刷新相关旧页面，允许重试；不关闭用户无关标签页 |
| 降级打开新数据 | 接入后的版本应拒绝不支持的格式并提示升级；不能保证没有保护逻辑的历史包安全读取 |

若尚有导入路径能直接绕过格式检查写入试点库，这是首期阻断项：先补该入口或明确禁用不支持格式，不能以“旧备份优化后做”为由留下污染新库的入口。

首期不提供自动反向迁移。成功升级后有新写入，不能直接恢复旧快照覆盖；应保留当前数据并通过修复版本前向处理。破坏性迁移必须先有可验证的恢复材料；本轮接管不自动清理历史备份。

已发布脚本原则上保持稳定。已成功升级的数据要用后续版本修正；若旧回调本身阻塞所有后续版本，允许最小修复该回调并记录原因，验证尚未升级、中途失败及已升级用户的路径，不能靠新增一个永远执行不到的版本解决。

## 9. 用户状态与诊断

复用现有加载/错误提示：显示“正在更新本地数据”、相关模块、错误原因和重试入口。不单独建设迁移管理页面、报表数据库或复杂进度系统。Dexie 普通升级无法提供可靠逐条进度时使用等待状态；已有分批迁移继续显示现有进度。

### 13.3 审查发现与修复

1. 新打开 B 先完成、旧打开 A 迟到时，A 可能覆盖连接引用，导致 B 未被 close 关闭。增加打开代次与尝试身份判断，迟到结果不能接管当前连接。
2. blocked 超时后，底层旧请求可能在阻塞解除时仍执行升级。增加仅用于取消和版本限制的窄原生请求适配，迟到升级事务中止；不恢复此前为不准确 mock 添加的事件归一化代理。
3. close 时若原生请求永久等待，不能继续等待其事件才结束。显式取消当前打开尝试，让外层 Promise 及时拒绝，迟到请求另行关闭或中止。
4. Dexie 对较新数据库的版本缺省重试不能作为兼容保证；试点明确拒绝高于支持版本的数据库，不清库、不写入。

相关回归覆盖了正常重开、打开失败重试、旧连接阻塞、A/B 完成顺序反转、超时后释放阻塞以及永不返回事件的取消。原有 outbox 写失败时整笔记录修改回滚的保护继续有效。
