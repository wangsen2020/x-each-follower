# 文档自动沉淀与时间顺序归档指令 (doc)

本指令用于在项目迭代、架构改造、功能新增或重大排障后，规范化总结并沉淀文档至 `docs/` 目录。用户可通过 `/doc` 调用；仅处理当前项目中值得复用的改进记录，不把琐碎修复机械扩写成文档。

---

## 一、前置判断：是否值得新建或写文档？

1. **值不值得写文档**：
   - ❌ **不写文档**：单行修复、typo、配置项微调、小样式微调等琐碎改动；
   - ✅ **写文档**：架构调整、跨文件重构、重大排障复盘（如 CDP 排障定位）、新模块或新功能等有复用价值的改动。
2. **按需求与迭代范围决定新建或更新**：
   - **新需求、新一轮迭代**：必须新建独立文档，并在文档时间顺序编号对照表中登记新的全局编号。即使发生在同一天、同一会话或相同模块，主题相关也不能作为追加旧文档的依据。
   - **同一需求的补充与验收**：纠错、方案细化、实施进展和验收结果更新该需求的原文档，保留原编号，不为每次补充另建文档。
   - 先遵守写文档价值门槛；不要因一次琐碎修复或单纯版本号变化机械新建文档。以需求目标、范围和交付内容判断是否进入新一轮迭代。
   - 与项目 `AGENTS.md` 的“新需求独立成文档”规则保持一致；废止按同天、同会话或主题相近强制合并的旧规则。

---

## 二、命名规范与格式约束

1. **文件命名格式**：
   ```text
   序号. 简要描述_日期_时间_{git用户名}.md
   ```
   - 序号后带空格（如 `5. 排障复盘-...`），与现有文档编号递增保持一致；
   - 日期时间：执行时读取当前本地实际时间（格式 `YYYYMMDD_HHMM`），不得根据历史记录猜测或复用旧时间；
   - git用户名：自动通过 `git config user.name` 获取（如 `wangsen`）；
   - **硬性禁止 ASCII 特殊字符 `( ) [ ]`**（防止截断 Markdown 链接），需要分隔时必须统一使用中划线 `-`；
   - **中文命名偏好**：新建文档标题及分类目录使用中文命名。发现已有实质性文档仍为英文或无意义名称时，结合其功能改为中文，并同步修复索引、正文交叉引用和其他仓库引用；不要改动图片、代码或第三方文件名。
2. **功能迭代分类存放**：
   - 如果有相同功能的迭代演进，在 `docs/` 下对应分类文件夹存放（如 `docs/互粉与粉丝管理/`、`docs/画像与标签系统/` 等）；若属于全新分类模块，则新建对应的中文目录。

---

## 三、文档时间顺序对照表维护规范

每次新建或实质性更新文档后，必须维护当前作者自己的对照表：`docs/文档时间顺序编号对照表_{git用户名}.md`。不要把不同作者的记录写进同一作者文件；遵循“谁的工作谁负责”，每位作者维护自己负责的文档和索引。各作者表中的全局序号仍须对应同一条清晰、可追溯的项目演进路线，避免各自编号冲突或出现时间倒置。

1. **可点击相对路径格式（必须严格遵守）**：
   - **必须以 `./` 开头**（相对于 `docs/` 目录），禁止使用裸路径；
   - **路径中的空格必须转义为 `%20`**（确保 CommonMark/WebStorm/GitHub 均可直接点击打开）；
   - 正确示例：`[179. xxx_20260607_2047_wangsen.md](./AI能力/179.%20xxx_20260607_2047_wangsen.md)`；
   - 错误示例：`[5. xxx](互粉与粉丝管理/5. xxx.md)`（缺 `./` 且空格未转义）。
2. **表格列顺序规范**：
   - 可点击链接列**必须**紧随「序号」列之后，即全表除序号外的第一列，说明/标题放在链接列之后；
   - 标准列序：
     ```markdown
     | 序号 | 文档 | 说明 | 创建时间 | 分类 |
     ```
   - 新增或调整记录必须严格按此列序排列，严禁将链接与说明位置颠倒。
   - 同一规则也适用于文档正文内指向 `docs/` 其他文档的交叉引用：链接相对当前 `docs/` 根目录、以 `./` 开头，空格写成 `%20`。编辑或重命名后，逐条核验目标存在、链接可点及编码正确。
3. **全局时间编号顺序**：
   - 新建文档时先检查 `docs/` 下全部实质性文档的创建先后，再分配连续的全局序号 `1. 2. ... N.`，不能只按当前分类文件夹局部编号。
   - 创建时间优先依据 Git 首次纳入版本控制的提交时间（例如 `git log --diff-filter=A`）；无 Git 记录时才使用现存文件时间并将不确定性作为判断依据。不要把最近修改时间误当成创建时间。
   - 若发现历史编号与创建先后不一致，调整前先盘点受影响的文件名、索引和交叉引用，再一次性同步更新，确保时间线连续且可追溯；不要每次调用都为无关文件制造重命名。

---

## 四、执行步骤

当用户触发 `/doc` 或要求总结沉淀文档时，按以下流程执行：

1. **获取环境信息**：
   - 执行 `git config user.name` 获取当前用户名；
   - 获取当前系统本地时间（YYYYMMDD_HHMM）；
   - 检视当前分支、近期 Git 提交和工作区状态（`git branch --show-current`、`git log -n 5`、`git status`），只总结本次实际完成且可核实的工作；区分本人、其他作者和未完成改动。
2. **确认需求范围与归档目标**：
   - 检查相关文档及项目 `AGENTS.md`，区分新需求、新一轮迭代与同一需求的补充或验收；不能仅凭日期、会话或主题相近决定合并。
   - 新需求、新一轮迭代按命名规则创建独立文档，分配新的全局编号并选择对应分类目录；相关旧文档可作为背景引用。
   - 同一需求的补充、纠错、细化和实施验收更新原文档，保留原编号并更新其对照表说明。
3. **编写/更新文档内容**：
   - 包含背景、问题或需求、根因（若适用）、解决思路、关键代码或文件对照及实际验证结果；未执行的检查明确标为未验证，不能声称流程已跑通。
4. **更新对照表**：
   - 更新 `docs/文档时间顺序编号对照表_{git用户名}.md`，核对 `./` 与 `%20` 链接、列序、目标文件和全库编号顺序；检查文档正文中的交叉引用。
5. **汇报结果**：
   - 向用户清晰汇报更新了哪篇文档，以及对照表追加的记录与可点击链接。
